# 我是 OOP

## 前言

对初学者来说，”面向对象程序设计“更像一次从程序设计基础走向更规范、更抽象、更可扩展写法的过渡。学习这门课时，读者会先接触字符串、顺序容器、库算法、输入输出流等基础工具，再逐步进入类、运算符重载、继承、多态、模板和资源管理这些更核心的内容。因此，真正重要的不是零散记住几个语法点，而是逐渐建立一种更清晰的程序组织方式。

本资料面向有 C 语言程序设计基础，但第一次系统学习面向对象程序设计的初学者，目标是帮助读者用较自然的方式理解基础概念、常见语法和典型程序结构，并在之后继续学习类、继承、多态和模板时，有一个足够稳定的出发点。

---

## 第一章 从字符串到批量数据

### 本章概要

很多人刚接触 C++ 时，会把注意力全部放在“它和 C 语言哪里不一样”上。这种比较当然有帮助，但还不够。更重要的是看清楚：C++ 希望程序员更多地借助**标准库**来表达问题，而不是凡事都从头手写。字符串不再只是字符数组，若干个数据也不必只靠固定长度数组保存，输入输出也不仅仅是“读一个数、打印一个数”这么简单。正是从这些地方开始，C++ 的风格逐渐和更早的过程式写法拉开了距离。

这一章主要讲四件事。第一，认识 C++ 程序最基本的外形，例如头文件、名字空间、输入输出流和 `main` 函数。第二，学会使用 `string` 处理文本，而不是继续把“字符串”仅仅理解成一串字符。第三，学会在不知道数据个数时，把一批数据放进 `vector` 这样的顺序容器里。第四，借助标准库算法 `sort` 对数据排序，并进一步计算中值。读完这一章后，读者应当能够写出一个完整的小程序：从输入中读入名字和成绩，保存一批作业分数，排序后取中值，再按指定精度输出结果。

### 1.1 从 Hello, world 到第一个完整程序

最经典的 C++ 程序通常写成下面这样：

```cpp
#include <iostream>

int main() {
    std::cout << "Hello, world!" << std::endl;
    return 0;
}
```

虽然代码很短，但它已经包含了后面会不断出现的几个基本对象。第一行 `#include <iostream>` 表示把标准输入输出流相关的声明引入当前程序。这里的 **头文件**（header）可以理解为“接口说明书”，它告诉编译器标准库里有哪些名字可以用。若不写这行，后面的 `std::cout` 和 `std::endl` 就没有合适的声明，程序通常无法通过编译。

`main` 是程序的入口函数，最后的 `return 0;` 则表示程序正常结束。这些我们在程序设计基础中已经学过了。

真正负责输出的是这一句：

```cpp
std::cout << "Hello, world!" << std::endl;
```

这里的 `std::cout` 是**标准输出流**（standard output stream），可以把它简单理解成“面向屏幕的输出通道”。右边的 `"Hello, world!"` 是一个字符串字面量，而 `std::endl` 的作用是结束当前这一行，并把缓冲区中的内容及时送出去。中间的 `<<` 叫作**输出运算符**，它把右边的内容送到左边的输出流中。

这一句之所以值得认真看，不只是因为它是第一条输出语句，更因为它体现了 C++ 的一个重要风格：把“输出”看成一个可以不断接收数据的流。例如下面这句同样合法：

```cpp
std::cout << "A = " << 3 << std::endl;
```

它的意思并不是“连续写了三条语句”，而是把多个输出动作串联在了一起。这里要特别注意：`<<` 在这种写法中是**左结合**的，也就是说程序会按从左到右的方式理解它。于是，这一整句等价于先把 `"A = "` 送进输出流，再把 `3` 送进去，最后再送一个换行结束符。

### 1.2 名字空间与 `std::`

初学 C++ 时，最容易反复看到的一个前缀就是 `std::`。它的含义其实并不复杂：`std` 是标准库使用的一个**名字空间**（namespace），而 `::` 是作用域解析运算符。写成 `std::cout`，就是在明确说明“这里说的 `cout` 来自名字空间 `std`”。

为什么要这样设计？因为大型程序中可能会出现大量重名。假如某个程序员自己也定义了一个叫 `cout` 的名字，而标准库里恰好也有一个 `cout`，那么编译器就会分不清到底在用谁。名字空间的作用，就是把相关名字装进不同的“抽屉”里，从而减少冲突。

刚开始写程序时，总是写 `std::cout`、`std::endl`、`std::string` 看上去有些繁琐，所以 C++ 提供了两种常见的简化方式。第一种是只引入少数常用名字：

```cpp
using std::cout;
using std::endl;
```

这样以后就可以直接写 `cout` 和 `endl`。第二种是

```cpp
using namespace std;
```

它表示把 `std` 里的所有名字都临时拿到当前作用域中。写起来确实更省事，但也更容易带来重名问题。因此，在入门阶段可以认识这种写法，但要知道它的本质是在“省略前缀”，而不是让 `std` 消失了。

### 1.3 `string`：把文本当成对象来处理

在更早的程序设计中，很多人第一次接触“字符串”时，是从字符数组开始的。C++ 标准库提供了 `string` 类型之后，文本处理就不必总依赖底层数组细节了。所谓 `string`，可以简单理解为：**用来保存零个或多个字符序列的对象**。它定义在头文件 `<string>` 中，因此使用前通常要写

```cpp
#include <string>
```

最基本的写法如下：

```cpp
std::string name;
std::cin >> name;
std::cout << "Hello, " << name << "!" << std::endl;
```

这里的 `name` 是一个 `string` 对象，`std::cin >> name` 表示从标准输入流中读入一个**连续的非空白字符串**。也就是说，如果输入是 `Xiao Ming`，那么 `>>` 默认只会先读到 `Xiao`，因为空格会被当作分隔符。这个特性以后会反复出现，因此最好现在就记住：**流输入运算符 `>>` 默认按空白分隔输入**。

把 `string` 看成对象之后，很多事情都会自然得多。比如说，字符串可以直接拼接：

```cpp
const std::string greeting = "Hello, " + name + "!";
```

这句代码之所以成立，是因为标准库已经为 `string` 定义好了合适的加法操作。这里就涉及三个非常重要的概念。

第一是**初始化**。`greeting` 在定义的同时就获得了初值，这和先定义、后赋值是两件不同的事。第二是**重载**（overload）。平时看到 `+`，常常会想到整数相加、实数相加；在这里，`+` 被赋予了适用于字符串的含义，即“把左边和右边的字符序列连接起来”。第三是**常量**。前面的 `const` 表示 `greeting` 一旦初始化完成，后面就不再允许被修改。

对初学者来说，这里最值得建立的观念是：在 C++ 里，许多熟悉的符号并不只服务于基本类型。只要某个类型被设计得足够完整，它也可以像整数、浮点数那样参与表达式。这正是“把数据和操作组织到一起”的一种体现。

### 1.4 构造函数、成员函数与 `size()`

当看到下面这些语句时：

```cpp
std::string name;
std::string hello = "Hello";
std::string first(10, '*');
```

读者会发现它们虽然都在“定义字符串”，写法却不完全一样。这是因为 `string` 作为一个类类型，可以通过不同方式构造出不同状态的对象。

最简单的 `std::string name;` 表示创建一个空字符串。`std::string hello = "Hello";` 表示用字面量 `"Hello"` 来初始化对象。`std::string first(10, '*');` 则表示构造一个由 10 个 `'*'` 组成的字符串。这里的这种“定义对象时顺便调用某种特殊初始化方式”的机制，正是**构造函数**（constructor）在起作用。

与之相配套的，还有**成员函数**（member function）。成员函数可以理解为“属于某个对象自己的函数”。例如：

```cpp
greeting.size()
```

中的 `size()` 就是 `string` 的成员函数，它返回字符串中字符的个数。写成 `greeting.size()`，意思是“向对象 `greeting` 询问它自己的长度”。这种写法和普通函数调用不同，普通函数像 `sort(a, b)` 那样把对象作为参数传进去；成员函数则是“由对象自己发起操作”。

当写出下面两句时：

```cpp
const std::string spaces(greeting.size(), ' ');
const std::string first(second.size(), '*');
```

程序的意思其实很直观。先取 `greeting` 的长度，再构造一个同样长、内容全是空格的字符串 `spaces`；接着根据另一行的长度，再构造一个由若干个星号组成的边框。这里 `size()` 返回的是长度，构造函数负责“按给定个数重复某个字符”。

在我们学习 `string` 时，一个很自然的练习，就是生成一个带边框的问候语。例如想得到这样的输出：

```text
********************
*                  *
* Hello, XiaoMing! *
*                  *
********************
```

如果直接一行一行手写，当然也能做出来，但那样做的程序几乎没有通用性。一旦名字长度变了，边框宽度就不对了。更合理的思路是先把中间真正要显示的问候语构造出来，再根据它的长度自动生成上下边框和空白行。

一种典型写法如下：

```cpp
const std::string greeting = "Hello, " + name + "!";
const std::string spaces(greeting.size(), ' ');
const std::string second = "* " + spaces + " *";
const std::string first(second.size(), '*');
```

这几句很值得反复体会。程序不是在“画图”，而是在**先构造若干有意义的字符串对象**。`greeting` 是真正的问候语；`spaces` 是一串和问候语一样长的空格；`second` 是中间空白行；`first` 是由星号组成的顶部和底部边框。等这些对象都准备好之后，输出就会变得非常机械：

```cpp
std::cout << first << std::endl;
std::cout << second << std::endl;
std::cout << "* " << greeting << " *" << std::endl;
std::cout << second << std::endl;
std::cout << first << std::endl;
```

这个例子看似简单，却体现了非常重要的程序设计思想：**不要急着输出，先把将要输出的内容组织清楚**。也就是说，程序并不只是“按顺序写几条命令”，更是在中间构造合适的数据，再让输出阶段自然发生。后面学类和对象时，这种“先组织数据，再调用操作”的思路会越来越重要。

### 1.5 `auto`、常见定义方式与“类型推断”

在 C++ 中，变量并不总要把完整类型手写出来。有些场合可以用 `auto` 让编译器自己推断类型。例如：

```cpp
auto size = greeting.size();
```

这句的意思是：把右边表达式的类型交给编译器判断，然后用这个类型去定义左边的变量 `size`。这样做的好处是，当右边类型较长、较复杂，或者根本不方便手写时，代码会简洁很多。

不过，`auto` 不是“万能偷懒”。它的前提是右边必须已经给出了足够明确的初值。例如：

```cpp
auto hello = "Hello";
```

这里推断出的并不是 `std::string`，而是更接近字符串字面量底层形式的类型。如果想得到真正的 `string` 对象，就必须非常清楚右边到底是什么。因此，入门阶段对 `auto` 的态度最好是：**把它当作方便工具，而不是避免理解类型的借口**。当右边类型很明确时可以使用；当右边类型本身就容易让人糊涂时，直接把类型写出来反而更稳妥。

### 1.6 当数据不止一个：为什么需要 `vector`

很多程序问题并不是只处理单个数值。例如，计算课程成绩时，期中和期末只有各一个分数，但作业成绩往往有一批。此时最自然的问题就是：这些作业分数该如何保存？

如果事先知道数据个数固定，那么用若干独立变量当然也能勉强处理；若个数很多，数组也能派上用场。但这里有一个关键困难：**在输入开始前，往往并不知道作业到底有多少次**。这时，固定长度的办法就很不灵活了。C++ 标准库给出的经典解决方案是 `vector`。

`vector` 是一种**顺序容器**（sequence container），也可以把它理解为一种“能自动增长的数组”。它里面的元素按线性顺序保存，可以通过位置访问对应元素，并且在需要时自动扩大自身容量。对于初学者来说，最重要的直观认识是：`vector` 既保留了数组“按下标访问”的方便，又避免了固定长度数组“不够大或浪费空间”的尴尬。

例如：

```cpp
std::vector<double> homework;
```

这表示定义一个空的 `vector`，里面准备存放 `double` 类型的元素。尖括号中的 `double` 告诉编译器：这个容器中每个位置保存的都是双精度浮点数。以后如果想保存字符串，也可以写成 `std::vector<std::string>`。

定义好容器之后，下一步通常就是把输入的作业成绩一项项放进去。典型代码如下：

```cpp
double x;
std::vector<double> homework;
while (std::cin >> x) {
    homework.push_back(x);
}
```

这段代码非常重要，因为它体现了两个核心知识点。

第一个知识点是 `push_back`。这个成员函数的含义是：**把一个新元素追加到容器末尾**。每读入一个成绩，就把它放到 `homework` 的最后面去。这样程序根本不需要提前知道一共有多少个成绩，因为容器会自己增长。

第二个知识点是 `while (std::cin >> x)` 这种写法。很多初学者第一次看到时会有些困惑：为什么输入语句本身能放在 `while` 条件里？原因在于，流输入表达式不仅会尝试读入数据，还会返回流对象本身的状态。若读取成功，条件就为真；若读取失败，例如到达输入结束或遇到非法输入，条件就为假，循环自然结束。

这是一种非常地道的写法，因为它把“读取一个数据”和“检查是否还能继续读取”合并在了一起。于是程序结构十分紧凑，也不容易写出“多读一次”或者“少检查一次”的错误。

当程序需要通过键盘手工结束输入时，通常要给出一个文件结束标志。在 Windows 系统中，常见做法是按 `Ctrl+Z`；在一些其他系统中，则常见为 `Ctrl+D`。从程序员角度看，更重要的不是记住按键本身，而是理解：**输入结束本身也是一种信号，流状态会据此变成失败，从而结束循环**。

### 1.7 `vector` 的大小、下标与 `size_type`

向 `vector` 中读完数据后，通常要先知道里面到底存了多少个元素。对应成员函数是

```cpp
homework.size()
```

它返回当前元素个数。例如：

```cpp
auto size = homework.size();
```

或

```cpp
std::vector<double>::size_type size = homework.size();
```

都可以用来保存结果。

这里为什么会出现看上去有些长的 `std::vector<double>::size_type`？原因在于，不同容器用于表示“长度”或“下标”的类型，理论上可以由它自己决定。标准库提供 `size_type`，就是在告诉程序员：“如果你要保存这个容器的大小，最好使用我自己推荐的类型。” 例如在后续，我们还会学到 `std::list`、`std::map` 等容器，它们都可以使用 `size_type`。

有时也会写成

```cpp
typedef std::vector<double>::size_type vec_sz;
vec_sz size = homework.size();
```

这表示给这个很长的类型起一个别名 `vec_sz`，以便后面重复使用。现代写法中，`auto` 往往更简洁，但知道 `size_type` 的存在仍然很重要，因为它体现了标准库容器“自己定义合适的相关类型”这一设计风格。

当需要访问第 `i` 个元素时，可以写

```cpp
homework[i]
```

这说明 `vector` 支持按位置直接访问，这也是它和链表相比的一个明显特点。不过，使用下标访问之前必须非常小心：只有当下标确实落在合法范围内时，这种访问才有意义。也就是说，若容器大小是 `size`，那么合法下标应当从 `0` 到 `size-1`。

### 1.8 先判断“有没有数据”

考虑这样一种情况：程序准备根据作业成绩计算中值，但用户根本没有输入任何作业分数。如果此时仍然强行取“中间元素”，程序就会立刻失去依据。于是，在真正排序和取中值之前，先检查 `vector` 是否为空，就是一件非常必要的事。

最直接的写法是：

```cpp
if (size == 0) {
    std::cout << "You must enter your grades." << std::endl;
    return 1;
}
```

这里的逻辑很简单：若元素个数为 0，就说明没有作业成绩，于是程序输出提示并提前结束。初学程序设计时，很多人容易把注意力全部放到“主要算法”上，却忽略“输入根本不满足前提怎么办”。事实上，程序真正稳不稳，往往就体现在这种前提检查上。

从更一般的角度说，编写程序时应该逐渐形成一个习惯：**在使用某个数据结构之前，先确认它确实处于可以被使用的状态**。对于 `vector` 来说，取下标前最好先知道它非空；对于输入流来说，使用读取结果前要先知道读取成功；对于字符串来说，拼接前要先知道对象已经被正确定义。这种思路后面会不断出现。

### 1.9 排序

若想计算一批数据的中值，最自然的前提就是先把它们按从小到大的顺序排好。C++ 标准库提供了现成的排序算法 `sort`，定义在头文件 `<algorithm>` 中。因此使用前通常要写

```cpp
#include <algorithm>
```

排序的典型写法是：

```cpp
sort(homework.begin(), homework.end());
```

这里最值得解释的是 `begin()` 和 `end()`。它们不是“第一个元素”和“最后一个元素”，而是两个**位置**。`begin()` 表示第一个元素所在的位置，`end()` 表示最后一个元素之后的位置。标准库算法经常使用这种半开区间 `[begin, end)` 的记法，即包含左端、不包含右端。这样设计的好处是：区间长度可以直接由两个位置的关系确定，而且空区间也更容易表达。

于是，`sort(homework.begin(), homework.end())` 的含义就是：对整个容器中的元素进行非递减排序。这里的“非递减”可以理解为从小到大排列，允许相邻元素相等。

对初学者来说，`sort` 的重要性在于它体现了 C++ 标准库的组织方式：**容器负责保存数据，算法负责处理数据，而算法通过位置范围来工作**。也就是说，`vector` 不一定自己带排序功能，但它可以把自己的元素范围交给标准算法 `sort` 去处理。这种“容器与算法分工”的思想，在后面还会不断出现。

### 1.10 输出精度

在我们输出数据时，常常需要控制输出格式。例如，希望结果保留 3 位有效数字时，可以写

```cpp
std::cout << std::setprecision(3) << value;
```

与之相关的头文件通常是 `<iomanip>`。`setprecision` 的作用是修改输出流的精度设置，使后续输出按指定精度显示。

有时程序并不想永久改变精度，而只是暂时改一下，输出完结果之后再恢复原状。这时可以先保存旧精度：

```cpp
std::streamsize prec = std::cout.precision();
```

然后输出时临时设置新精度，最后再恢复：

```cpp
std::cout << std::setprecision(3) << value << std::setprecision(prec);
```

这里的 `streamsize` 是与流精度相关的类型。我们当然也可以把 `prec` 定义为 `int`，但既然标准库提供了专门的类型，就最好顺着它的设计去写。

若想固定保留若干位小数，还可以配合

```cpp
std::cout.setf(std::ios::fixed);
std::cout << std::setprecision(1);
```

一起使用。这样输出 `3.14159` 时，就会更接近“保留 1 位小数”的效果，而不是简单地控制有效数字个数。

### 1.11 本章小结

这一章真正要建立起来的，不只是若干语法点，而是一种新的程序组织习惯。文本应当优先交给 `string` 处理，而不是急着退回字符数组；若数据个数未知，就应当考虑 `vector` 这样的动态容器；容器中的数据可以交给标准库算法处理，而不是每件事都自己从头写；输入不仅仅是“读值”，还要顺手检查流状态；输出不仅仅是“打印结果”，还要考虑精度和格式。

如果把这些内容贯通起来，可以把本章概括为一句话：**C++ 程序设计的基础，不在于记住更多零散语法，而在于学会借助库中的对象、容器和算法，更自然地表达问题。**

## 第二章 用函数、结构体和容器组织程序

### 本章概要

写程序时，真正困难的地方往往不在某一行语法，而在于：当问题一变大，代码如何继续保持清楚。前一章里，程序还只是“读入一些数据，再算一个结果”；到了这一章，问题已经开始发生变化。我们不再只处理一个名字、一个分数、一个向量，而是要把“计算成绩”“读取作业”“保存学生记录”“筛选不及格学生”“排序并生成报表”这些事情组织成一个更完整的程序。也就是说，本章的重点不只是新增几个语法点，而是开始学习**怎样把程序拆开、怎样把数据装起来、怎样让不同部分彼此配合**。

这一章主要讨论五件事。第一，为什么要把重复计算封装成函数，以及函数的不同参数形式分别适合什么场景。第二，什么是异常，为什么有些错误不适合只靠返回值处理。第三，什么是引用，它和指针有什么关系，又为什么它在函数参数里格外重要。第四，如何用 `struct` 把原本分散的数据组织成一条完整记录。第五，如何进一步使用 `vector`、`list`、迭代器和 `map` 处理一批更复杂的数据。读完这一章后，读者应当能够把一个较长的小程序拆成多个函数和多个文件，理解“按值传递”“按引用传递”“按 `const` 引用传递”的区别，并能较自然地在顺序容器中遍历、删除、筛选和排序元素。

### 2.1 当代码开始重复：为什么需要函数

我们知道，具体的计算方法，若程序里只算一次，直接写出来也未尝不可。但只要它出现第二次、第三次，问题就来了。首先，代码会变长，读起来不够整洁；其次，一旦权重规则将来需要改动，就必须把每一处都找出来修改；最后，别人读代码时也看不出“这一长串表达式到底想表示什么”。因此，更自然的做法是把它封装成一个有名字的函数。例如，

```cpp
double grade(double midterm, double final, double homework)
{
    return 0.2 * midterm + 0.4 * final + 0.4 * homework;
}
```

这样做之后，原本冗长的输出语句就能写成

```cpp
cout << grade(midterm, final, homework);
```

这类写法的好处并不只是“省几行代码”，而是把“怎么计算”与“在哪里使用”分开了。调用函数的地方只关心“我要成绩”，而函数内部负责“成绩怎么算”。这正是组织程序最基本的方式之一：**把一段有明确意义的计算单独起一个名字**。

从程序设计的角度看，库程序往往也具有类似特征。它通常解决某一类较明确的问题，有自己的名称，而且可以相对独立地被其他部分调用。换句话说，程序一旦变大，最基本的组织手段其实只有两类：一种是**用函数组织计算**，另一种是**用数据结构组织信息**。这一章讨论的很多内容，最后都可以归回到这两件事上。

### 2.2 函数的不同写法：按值、按引用与 `const` 引用

初学函数时，最先接触到的通常是“按值传递”。例如上面的 `grade(double, double, double)`，三个参数都是值参数。所谓按值传递，就是调用函数时把实参的值复制一份交给形参。这样做的优点是简单、安全，函数内部改动形参不会影响外面的实参。

但是，按值传递并不总是划算。若参数只是一个 `double` 或 `int`，复制的代价几乎可以忽略；若参数是一个很长的 `vector<double>`，复制整份数据就可能非常浪费。于是，C++ 提供了**引用**（reference）这种机制。

引用最简单的理解方式，就是“给已有对象起一个别名”。例如：

```cpp
int i = 3;
int& ii = i;
```

这里 `ii` 并不是一个新的整数对象，而是 `i` 的另一个名字。对 `ii` 的操作，本质上就是对 `i` 的操作。也正因为如此，引用在函数参数中特别有用：它可以让函数直接访问实参本身，而不是先复制一份临时副本。在函数内部对这个引用对象的修改，会使得函数外部的实参也发生改变。

不过，若函数只是想“直接看一眼这个对象”，并不打算修改它，那么最好再加上 `const`。例如：

```cpp
double grade(double midterm, double final, const std::vector<double>& hw)
```

这里的 `const std::vector<double>& hw` 表示：`hw` 是通过引用传进来的，因此不会复制整个向量；同时前面的 `const` 又保证函数不会去改动这份作业数据。于是，这种参数形式兼具两方面优点：**高效**，并且**不会误改实参**。在后续的 C++ 程序中，这种写法会非常频繁，因此必须尽早习惯。

把三种常见形式放在一起看，会更清楚：

```cpp
double median(std::vector<double> vec);
double grade(double midterm, double final, const std::vector<double>& hw);
std::istream& read_hw(std::istream& in, std::vector<double>& hw);
```

第一种 `median` 选择按值传递，是因为它内部可能要排序算中值，而排序会改动向量。由于我们不想影响原数据，必须复制一份再改。第二种 `grade` 选择按 `const` 引用传递，是因为它只读取作业成绩，不应修改它们，同时又不想多做一份拷贝。第三种 `read_hw` 选择普通引用传递，是因为它的任务就是把读入的数据写进容器里，这本来就必须改动实参。

### 2.3 异常处理

假设有一个计算成绩的程序。若一批作业成绩已经放在向量里，那么中值可以写成一个独立函数：

```cpp
double median(std::vector<double> vec)
{
    typedef std::vector<double>::size_type vec_sz;
    vec_sz size = vec.size();
    if (size == 0)
        throw std::domain_error("median of an empty vector");
    sort(vec.begin(), vec.end());
    vec_sz mid = size / 2;
    return size % 2 == 0 ? (vec[mid] + vec[mid - 1]) / 2 : vec[mid];
}
```

这个函数里最关键的一句，是

```cpp
throw std::domain_error("median of an empty vector");
```

它表示：函数发现自己当前收到了一个不能接受的实参，于是主动抛出一个异常。这里的 `std::domain_error` 属于标准库中的一种异常类型，常用来表示“参数值落在函数不能处理的范围中”。对于中值函数来说，空向量正是这样一种不合法输入，因为“空数据的中值”根本没有意义。

很多初学者会问：这里为什么不直接返回 `0` 呢？原因在于，`0` 也是一个完全可能的正常数值。若把“真的中值等于 0”和“因为没有数据所以胡乱返回 0”混在一起，调用者就无法分辨真实情况。异常的意义，恰恰是在说：**这里不是算出了一个特殊结果，而是问题本身就已经无法继续按正常流程计算**。

异常抛出之后，程序并不是立刻崩溃，而是会把控制权交给能够处理它的地方。例如：

```cpp
try {
    double final_grade = grade(midterm, final, homework);
    cout << final_grade << endl;
} catch (std::domain_error e) {
    cout << e.what() << endl;
}
```

这里 `try` 语句块表示“先尝试执行这些代码”；若执行过程中抛出了对应类型的异常，程序就会跳转到 `catch` 语句块中处理。`e.what()` 则会返回一段描述性文字，也就是当时构造异常对象时附带的那条消息。

这种写法背后其实是一种更成熟的程序组织方式：**真正出错的地方负责发现错误，而更高一层的调用者决定如何处理错误**。例如，中值函数只负责判断“空向量不能求中值”；至于遇到这种情况时是打印提示、终止程序，还是记录日志，应该由调用它的更外层逻辑来决定。

### 2.4 函数重载

当程序继续演化时，会出现一种很自然的需求：有时候同一个需求（例如计算成绩），我们所能提供的信息（即参数类型）是不一样的。如果分别起两个完全不同的函数名，当然也能做，但可读性并不总是最好。C++ 提供了**重载**（overload），允许多个函数使用同一个名字，只要参数列表不同即可。

例如：

```cpp
double grade(double midterm, double final, double homework)
{
    return 0.2 * midterm + 0.4 * final + 0.4 * homework;
}

double grade(double midterm, double final, const std::vector<double>& hw)
{
    if (hw.size() == 0)
        throw std::domain_error("student has done no homework");
    return grade(midterm, final, median(hw));
}
```

这两个函数都叫 `grade`，但一个的第三个参数是单个分数，另一个的第三个参数是作业向量。编译器会根据实参类型自动选择匹配版本。这样做的好处在于：无论是“直接根据作业中值算成绩”，还是“先由函数内部算出中值再算成绩”，对调用者来说都统一成了“求成绩”这一件事。

重载的思想非常值得体会。它并不是为了炫技，而是在表达：**这几种操作本质上属于同一类事情，只是输入形式不同**。只要这个判断成立，使用同一个函数名通常会让程序更整洁，也更符合人的思维方式。

### 2.5 引用

前面已经把引用当作“别名”用过了，但这一节需要把它讲得更清楚一些。

在程序里，标识一个对象通常有三种方式：直接用对象自己的名字，用指针保存对象地址，再或者用引用给对象再起一个名字。引用与指针确实很像，因为它们都能“间接地指向某个对象”；但它们并不相同。

最关键的区别有两点。第一，**引用在定义时必须初始化**。例如：

```cpp
int i = 0;
int& r = i;
```

这是合法的；但如果只写 `int& r;`，就不合法。第二，一旦引用绑定到某个对象之后，它就不会再改绑到别的对象上。也就是说，引用没有“后来再指向谁”的问题，它自始至终都是那个对象的别名。

指针则不同。指针本身是一个变量，它保存的是地址，因此它可以在程序运行过程中反复改写，今天指向 `a`，明天指向 `b`，也可以暂时为空。引用没有这种“空着”或“改指向”的状态，所以它在语义上往往更直接、更安全。

也正因为引用并不是“可自由改向的指针”，所以有些说法需要格外小心。比如说，可以有“指针的引用”，但没有“引用的引用”这种独立概念需要程序员去操心。这里不是说不能给对象的别名再起一个别名（这样这些别名就都指向一个对象了），而是说不存在 `int& & r = a;` 这种写法。同时，引用也不能是 `void` 类型，不能有“空引用”，不能真正形成“引用数组”那样的独立结构。入门阶段，最重要的是记住一条根本原则：**引用更像一个已经绑定好的别名，而不是一个可随时改写的地址盒子**。

虽然引用在函数参数中最常见，但它也可以出现在返回值位置。我们先看一个合法例子：

```cpp
int& f(int a[], int index)
{
    return a[index];
}
```

这个函数返回数组中某个元素的引用，因此调用结果本身也可以出现在赋值号左边，例如：

```cpp
f(s, 3) = 22;
```

这行代码的含义并不是“给函数返回值赋值”这么神秘，而是：`f(s, 3)` 实际上引用到了 `s[3]`，因此这句等价于把 `s[3]` 改成 `22`。

不过，返回引用时有一条极重要的边界：**函数不能返回局部自动变量的引用**。例如下面这种写法是错误的：

```cpp
int& g(int a[], int index)
{
    int r = a[index];
    return r;
}
```

原因在于，`r` 是函数内部的局部变量，函数结束后它就被销毁了。此时若还把对它的引用交给外部使用，就相当于把一个已经不存在的对象当成还活着来访问，这会导致未定义行为。

所以，判断“能不能返回引用”时，最朴素也最可靠的方法就是问自己：**被返回的那个对象，在函数结束之后还存在吗**？若答案是否定的，就绝不能返回对它的引用。

### 2.6 输入流的使用

输入流的使用也是 C++ 中的一个常用知识。我们先来看一个简单的例子。如果程序里有一整段逻辑专门负责把作业成绩读进向量，那么这段逻辑也完全可以单独封装。一个典型写法是：

```cpp
std::istream& read_hw(std::istream& in, std::vector<double>& hw)
{
    if (in) {
        hw.clear();
        double x;
        while (in >> x) {
            hw.push_back(x);
        }
        in.clear();
    }
    return in;
}
```

这里有几个值得仔细看的点。第一，函数返回值是 `std::istream&`，也就是输入流的引用。这样一来，调用者既可以单独写

```cpp
read_hw(cin, homework);
```

也可以把返回结果直接放进条件判断中：

```cpp
if (read_hw(cin, homework)) {
    // ...
}
```

第二，参数 `hw` 使用普通引用传递，因为函数要清空它、再往里写入新数据，这显然属于“需要修改实参”的情况。第三，函数内部的 `hw.clear()` 也很重要，它表示若这个容器原本可能已经有旧数据，那么开始新一轮读取前应当先清空。

第四，循环结束后调用 `in.clear()`，是为了把因为读取结束而进入失败状态的输入流恢复到可用状态。很多初学者第一次看到这句会觉得突兀，但它其实很合理：若上一轮读取是因为到达输入结尾而停下来的，那么流对象会记住“刚刚失败过”。如果不把这个状态清掉，后面程序再想继续使用这个流，就可能一直处在失败状态中。

从这个函数可以看出，程序设计里的很多“细节”其实都与责任分工有关：函数不仅要把作业成绩读进去，还要负责把容器准备好、把流状态恢复好，这样调用它的代码才能更放心地继续往下走。

### 2.7 用 `struct` 组织一条完整记录

当程序要处理的不再只是单条信息，单靠几个彼此独立的变量就会越来越乱。比如说，一个学生至少包含姓名、期中成绩、期末成绩和整批作业分数。若这些东西分别散落在多个变量中，程序既不容易读，也不容易维护。更自然的办法，是把它们打包成一个整体。

最基础的写法就是 `struct`：

```cpp
struct Student_info {
    std::string name;
    double midterm, final;
    std::vector<double> homework;
};
```

这里的 `Student_info` 可以理解为“学生信息记录”这种数据结构。它把一个学生相关的几个成员放在一起，于是程序里就不再是“这个名字对应哪个期末成绩来着”，而是明确地写成 `record.name`、`record.midterm`、`record.homework`。这会让代码的可读性提高很多。

一旦有了这种结构，就可以很自然地定义

```cpp
std::vector<Student_info> students;
```

这表示“一个学生记录的向量”。也就是说，程序保存的不再只是“一批分数”，而是“一批学生对象”。从这里开始，数据组织就进入了新的层次：向量里的每个元素本身又是一个小结构。

在这里，如果我们想要对 `struct` 结构体排序，应该怎么做呢？例如，若想按姓名排序，则可以写一个比较函数：

```cpp
bool compare(const Student_info& x, const Student_info& y)
{
    return x.name < y.name;
}
```

这个函数通常被称为**谓词**（predicate）。在很多标准库算法里，谓词就是一个返回布尔值的函数，用来告诉算法“两个元素之间应当怎样比较”或者“某个元素是否满足条件”。只要把“谓词就是一个能回答是或否的问题的函数”这层意思抓住，后面使用算法时就不会那么陌生。

后续，我们就可以通过这样的方法来按照姓名排序学生：

```cpp
sort(students.begin(), students.end(), compare);
```

而后续在打印报表时，我们常常见到诸如这样的很有代表性的细节：

```cpp
cout << students[i].name
     << string(maxlen + 1 - students[i].name.size(), ' ');
```

这里临时构造了一个没有名字的 `string` 对象，用来补足空格。这样的对象通常叫**无名对象**或**临时对象**。它并不需要先取个变量名，因为它只在这一处表达式里短暂存在，表达式结束后就没有继续保留的必要了。理解这一点后，就会明白：对象并不一定都要先“站住脚”，有时它们只需在表达式中临时发挥一次作用。

### 2.8 顺序容器不只有 `vector`：`list` 的价值

前面主要使用的是 `vector`，因为它支持下标、顺序紧凑、随机访问很方便。但当程序开始频繁删除中间元素时，`vector` 的缺点就会暴露出来。考虑这样的问题：从一批学生中把不及格者提取出来。

最直接的方法是准备两个向量，一个保存及格学生，一个保存不及格学生：

```cpp
std::vector<Student_info> extract_fails(std::vector<Student_info>& students)
{
    std::vector<Student_info> pass, fail;
    for (std::vector<Student_info>::size_type i = 0; i != students.size(); ++i) {
        if (fgrade(students[i])) {
            fail.push_back(students[i]);
        } else {
            pass.push_back(students[i]);
        }
    }
    students = pass;
    return fail;
}
```

这种写法的思路很直接，但它会额外保存许多副本。于是，人们自然会想到第二种办法：一边扫描原向量，一边用 `erase` 把不及格者移走。这比“双向量复制”省内存一些，但又带来了新问题。`vector` 删除中间元素后，后面的所有元素都要往前移动一格，因此这种操作在大数据规模下会越来越费时，且可能出错。换句话说，`vector` 很适合“按位置快速读取”，却不特别适合“在中间频繁插入和删除”。

这时就可以考虑另一种顺序容器：`list`。`list` 的特点是更擅长顺序访问，中间插入和删除通常比 `vector` 更高效，但它不支持像 `v[i]` 那样按下标直接取第 `i` 个元素。于是，这里就出现了一个非常典型的性能权衡：**如果主要需求是随机访问，`vector` 往往更合适；如果主要需求是大量中间插入和删除，`list` 往往更合适。**

把两者放在一起比较，最容易记住的结论有三条。

第一，`vector` 支持随机访问，也就是可以快速使用下标访问任意位置的元素；`list` 不支持这种访问方式，因此 `list[i]` 是不成立的。第二，对于大型数据，`list` 在中间插入和删除通常比 `vector` 更快，因为它不需要整体搬动后续元素。第三，`vector` 的顺序访问通常更快、内存布局也更紧凑，因此在很多“主要是读取和遍历”的场景里，它仍然往往是优先选择。

这说明“应该用哪个容器”不是一个只靠背结论的问题，而是要看具体任务。若程序经常要按下标取第 `k` 个元素，`vector` 更自然；若程序经常在中间位置删除或插入，`list` 更合适。真正成熟的写法，不是死守某一种容器，而是根据操作模式来选。

排序时也会体现这种差异。标准库里的通用 `sort` 算法要求较强的随机访问能力，因此它可以直接处理 `vector`，却不能直接处理 `list`。`list` 往往需要调用自己的成员函数 `sort()`。这再次说明：虽然各种容器都属于标准库体系，但它们能提供的操作能力并不完全一样。

### 2.9 迭代器：容器与算法之间的桥梁

当程序既要支持 `vector`，又要支持 `list` 时，单纯依赖下标就不够用了，因为 `list` 没有 `list[i]` 这种操作。C++ 标准库为此提供了**迭代器**（iterator）。

可以把迭代器理解为一种“位置值”。它既标识了某个容器，也标识了容器中的某个位置，并且允许程序从这个位置读取元素、修改元素，或者向前移动到下一个位置。换句话说，迭代器不是元素本身，而是“指向元素的访问入口”。

例如，对学生向量逐个输出姓名，可以写成

```cpp
for (std::vector<Student_info>::const_iterator iter = students.begin();
     iter != students.end(); ++iter) {
    cout << (*iter).name << endl;
}
```

这里的 `iter` 就是一个迭代器。`students.begin()` 表示容器第一个元素的位置，`students.end()` 表示最后一个元素之后的位置。表达式 `*iter` 表示“取出当前位置的元素”，因此 `(*iter).name` 就是在访问当前这条学生记录的 `name` 成员。

如果觉得 `(*iter).name` 这种写法不够方便，还可以使用箭头运算符：

```cpp
iter->name
```

它和 `(*iter).name` 的效果相同，只是写法更紧凑。对初学者来说，最重要的是知道这两种形式本质一致：箭头只是为了在“先解引用，再取成员”这种场景中写得更自然。

标准库容器通常都定义了两种相关迭代器类型：`iterator` 和 `const_iterator`。前者允许通过迭代器修改元素，后者只允许读取，不允许修改。若只是遍历输出，使用 `const_iterator` 更稳妥；若后面要删除、替换或更新元素，则需要使用普通 `iterator`。

进而，我们把前面的“提取不及格学生”问题用迭代器重写后，就能得到更通用的版本：

```cpp
std::vector<Student_info> extract_fails(std::vector<Student_info>& students)
{
    std::vector<Student_info> fail;
    for (std::vector<Student_info>::iterator iter = students.begin();
         iter != students.end();) {
        if (fgrade(*iter)) {
            fail.push_back(*iter);
            iter = students.erase(iter);
        } else {
            ++iter;
        }
    }
    return fail;
}
```

这里最关键的一句是

```cpp
iter = students.erase(iter);
```

许多人第一次看到时会疑惑：为什么 `erase` 之后还要把返回值赋回给 `iter`？原因在于，删除一个元素之后，原来的那个位置已经不再有效了。如果还继续使用旧迭代器，就会出现错误。标准库的约定是：`erase` 会返回一个新的迭代器，指向**被删除元素后面原本跟着的那个元素**。于是，程序只要接住这个返回值，就能从正确的新位置继续遍历。

这一点非常重要，因为它揭示了“删除元素”与“继续遍历”之间的正确衔接方式。尤其是当容器结构会变化时，程序必须始终意识到：有些旧位置已经失效，不能想当然地继续用。类似思想在 `list` 中也一样成立。

虽然 `vector` 和 `list` 的底层结构不同，但这种迭代器式删除写法却可以统一起来。这也正是标准库设计的优点之一：只要掌握了容器、迭代器和算法之间的基本关系，许多操作方式就能在不同容器之间迁移。

### 2.10 `map`：键值对存储的思想

到这里为止，我们接触的主要都是顺序容器，也就是元素按线性顺序排开的结构。但程序里还有另一类很常见的需求：根据“键”去找“值”。例如，想把编号和身份、单词和解释、学号和姓名对应起来，此时只用 `vector` 就不太自然了。

这时可以使用 `map`。`map` 是一种**关联式容器**（associative container），其中每个元素都是一个键值对 `(key, value)`。它会按照键来组织数据，并且同一个键通常是唯一的。

例如：

```cpp
std::map<int, std::string> m;
m.insert({2, "c"});
m.insert({4, "c++"});
m.insert({5, "python"});
```

这里键是整数，值是字符串。遍历时，常见写法是：

```cpp
for (auto iter = m.begin(); iter != m.end(); ++iter) {
    cout << iter->first << " " << iter->second << endl;
}
```

之所以写成 `first` 和 `second`，是因为 `map` 中每个元素本质上都是一个二元组：前一部分是键，后一部分是值。

`map` 与前面的顺序容器很不一样。读者现在至少要建立三层认识。第一，它不是靠下标保存“第几个元素”，而是靠键来组织“哪个值对应哪个键”。第二，它内部通常会按照键排序，因此遍历 `map` 时，元素往往会按键的顺序出现。第三，它很适合做查找、插入、修改这类“按键进行”的操作。

对于初学阶段来说，了解 `map` 的几种常见成员就够用了，例如 `insert`、`emplace`、`erase`、`size`、`empty`、`clear`、`operator[]` 和 `at()`。其中 `operator[]` 很常见，例如：

```cpp
m[10] = "shell";
```

这行代码表示把键 `10` 对应的值设为 `"shell"`。若这个键原本不存在，容器会为它创建新元素；若原本已经存在，则会把旧值替换掉。

其他几种常见的操作例如：

```cpp
myMap.insert(std::make_pair(1, "Apple")); // make_pair 表示创建一个键值对
myMap.insert({2, "Banana"}); // 也可以直接使用初始化列表插入
myMap.emplace(3, "Cherry"); // emplace 也是插入，但是会直接在容器内创建，比 insert 效率高一些
myMap.erase(2); // 根据键值删除
std::cout << myMap.size() << std::endl; // 输出容器中的键值对数量 
```

### 2.11 把程序拆到多个文件中

当函数和数据结构越来越多时，把所有代码都塞进一个源文件就会越来越难维护。这时，程序通常要拆成多个文件。最常见的分工方式是：把函数声明和结构声明放进头文件 `.h` 中，把具体定义放进源文件 `.cpp` 中。

例如，中值函数可以拆成：

```cpp
// median.h
double median(std::vector<double> vec);
```

和

```cpp
// median.cpp
double median(std::vector<double> vec)
{
    // ...
}
```

头文件更像是“对外说明接口”，源文件则真正提供实现。这样做的意义在于：别的文件如果只想调用 `median`，只需要知道它“怎么被使用”，未必要看到完整实现。同时，`main.cpp` 也就只负责总体流程，而不必承载所有细节。程序结构会更清楚，后续修改和调试也更方便。

头文件中常常还会看到类似下面的写法：

```cpp
#ifndef GUARD_median_h
#define GUARD_median_h
// ...
#endif
```

这是头文件保护（include guard），作用是防止同一个头文件在一次编译过程中被重复包含多次。入门阶段只要先知道它的作用即可，不必急于记住名字本身该怎么取。重要的是理解：**程序一旦拆成多个文件，重复包含和声明冲突就会成为新的工程问题，因此也需要新的组织手段。**

### 2.12 本章小结

这一章真正要建立的，不只是几个新语法，而是一种更成熟的程序组织观念。函数让我们把重复计算抽离出来，并通过参数形式明确“复制”“只读访问”和“原地修改”的区别。异常让程序能够把“正常结果”和“无法继续计算”区分开来。引用让函数既可以避免不必要的拷贝，又能在需要时直接操作实参。`struct` 则让原本分散的数据成为一条完整记录。进一步地，`vector`、`list`、迭代器和 `map` 又把“如何保存一批数据”“如何遍历它们”“如何删改它们”“如何按键查找它们”这些问题纳入了统一的标准库体系中。

### 本章小练习

1. 填空题  
若函数只需要读取一个 `std::vector<double>`，不需要修改它，同时又想避免复制整个向量，那么形参更合适写成 `________________`。

2. 程序题  
已知 `std::vector<Student_info> students;`，以及函数 `bool fgrade(const Student_info& s);` 已经写好。请用迭代器写出一段循环，把所有不及格学生放入另一个向量 `fail` 中，并且从 `students` 中删除他们。只需写循环主体即可。

### 参考解答

1. 可以写成

```cpp
const std::vector<double>& hw
```

这样写的原因是：引用避免了整份向量的复制，`const` 又保证函数不会修改原数据，因此既高效又安全。

2. 一种典型写法如下：

```cpp
for (std::vector<Student_info>::iterator iter = students.begin();
     iter != students.end();) {
    if (fgrade(*iter)) {
        fail.push_back(*iter);
        iter = students.erase(iter);
    } else {
        ++iter;
    }
}
```

这里必须把 `erase` 的返回值重新赋给 `iter`，因为删除当前元素后，原来的迭代器已经不再适合继续使用，新的返回值才指向删除位置之后的下一个有效元素。

## 第三章 用算法和模板提升程序的通用性

### 本章概要

前两章已经建立了两个很重要的基础。第一，程序中的数据不必总是散着放，可以组织成字符串、向量、结构体等更清楚的对象。第二，程序中的操作不必总是直接写在 `main` 里，可以逐步拆成若干函数。这一章继续向前走一步，讨论另一个更深的问题：**如果相同的处理逻辑会反复出现在不同容器、不同数据类型甚至不同程序里，那么能不能把它们进一步抽象出来，使一份代码适用于更多场景**。

为了解决这个问题，C++ 标准库提供了两个极其重要的工具。一个是**库算法**，也就是由标准库直接给出的通用处理过程，例如查找、复制、变换、累加、删除、分割、分类、排序等。另一个是**泛型函数**，也就是模板函数。它允许程序员把“对某一种类型成立的操作模式”推广为“对一大类类型都成立的操作模式”。这两者之所以能够配合得很好，是因为它们都依赖同一个桥梁：**迭代器**。

因此，这一章最核心的主题其实只有一句话：**算法不必依附于某一种具体容器，函数也不必只为某一种具体类型而写。** 只要数据能通过统一的接口被访问，程序就可以写得更短、更灵活，也更接近真正可复用的形式。

### 3.1 为什么要使用库算法

程序写久了之后，人们很快会发现：很多处理过程其实非常相似。比如把一个区间中的元素逐个复制到另一个地方，把容器里的某些元素找出来，把满足条件的元素保留下来，把每个元素映射成另一个值，再把结果累加、排序或分类。这些工作看上去各不相同，但本质上都属于“在一段数据上进行重复规则操作”。

若每次都自己写 `for` 循环，当然也能完成任务，但这样做会带来三个问题。第一，代码容易重复，而且不同地方可能写出略有差别的版本。第二，细节错误很多，例如边界写错、迭代器移动错、删除元素后位置失效等。第三，代码表达力不够强。对读程序的人来说，`for` 循环里究竟是在“复制”“筛选”“计数”还是“变换”，常常要读完整段代码才能看明白。

标准库算法正是为了解决这些问题而设计的。它们把常见处理模式直接做成现成接口，只要给出一个范围，再给出必要的规则，算法就能替程序员完成工作。这样写出来的程序往往更短，也更容易从名字上直接看出意图。

例如，若想把一个字符串向量 `bottom` 追加到另一个向量 `ret` 末尾，最直接的办法当然可以手写循环：

```cpp
for (std::vector<std::string>::const_iterator it = bottom.begin();
     it != bottom.end(); ++it) {
    ret.push_back(*it);
}
```

但如果把这个动作抽象成“复制一个区间到另一个目的地”，就可以使用标准库算法：

```cpp
copy(bottom.begin(), bottom.end(), back_inserter(ret));
```

这句代码比循环更短，但更重要的是，它更直接地表达了意图：这里要做的是**复制**，而不是“自己手搓一个循环”。程序一旦开始大量使用库算法，整体风格会发生明显变化：代码不再围绕“逐个元素怎么处理”展开，而更多围绕“这段数据想做什么操作”展开。

### 3.2 范围、迭代器和数据结构独立性

标准库算法之所以能适用于不同容器，关键就在于它们通常并不直接接收容器本身，而是接收一对迭代器，表示一个**范围**（range）。最典型的形式是

```cpp
[begin, end)
```

这仍然是前面已经见过的半开区间，包含 `begin` 所指的位置，不包含 `end` 所指的位置。只要某个容器能提供 `begin()` 和 `end()` 这样的入口，很多算法就可以直接拿来用。

这带来的一个极其重要的结果是：**算法获得了对底层数据结构的独立性。** 换句话说，算法并不需要知道底层到底是 `vector`、`string` 还是 `list`；它只需要知道：我手里的这两个迭代器能否支持我需要的那些基本操作。

这种思想非常值得反复体会。传统写法往往会把“数据怎么存”和“数据怎么处理”牢牢绑在一起，而标准库的做法是把它们分开。容器负责保存元素，迭代器负责暴露统一访问方式，算法则只依赖这种访问方式来完成工作。于是，同一个算法可以在多种容器上重用，而同一个容器也可以搭配大量不同算法。

这就是本章最重要的抽象思想之一。它看似只是接口设计，实际上已经在悄悄改变程序员思考问题的方式：**先问需要什么访问能力，再问用什么容器，而不是反过来。**

### 3.3 `copy`、`insert` 与适配器 `back_inserter`

在库算法中，`copy` 是最容易理解、也最值得首先掌握的一个：

```cpp
copy(begin, end, out);
```

它的含义是：把区间 `[begin, end)` 中的所有元素，按顺序复制到从 `out` 开始的目的地中去。这个定义本身看上去并不难，但真正容易出错的是第三个参数到底该怎么给。

很多初学者第一次看到下面这句时，会自然地觉得它应该成立：

```cpp
copy(bottom.begin(), bottom.end(), ret.end());
```

但这其实通常是错误的。原因在于，`ret.end()` 只是“已有元素之后的那个位置”，它本身并不等于“这里已经准备好一段足够大的空间，供你往后写”。如果目标容器还没有提前扩容，直接往 `end()` 后面写入就是越界性质的错误。

解决这个问题的自然办法之一，是使用**适配器**（adapter）`back_inserter`：

```cpp
copy(bottom.begin(), bottom.end(), back_inserter(ret));
```

`back_inserter(ret)` 并不是普通意义上的元素位置，而是一个特殊的输出迭代器。每当 `copy` 想往这个“位置”写一个元素时，它实际上会转化为对 `ret.push_back(...)` 的调用。也就是说，算法本身只负责“我要把元素交给目的地”，而适配器负责把这个动作解释成“追加到容器末尾”。

适配器的意义就在这里：它把“算法期望的接口”和“容器真实提供的操作”接在了一起，使两者能够自然配合。理解 `back_inserter` 之后，就会明白为什么标准库风格强调“把复制元素”和“在容器末尾插入元素”分离开来。算法和容器各司其职，而适配器负责搭桥。

当然，若程序员提前手动分配好了足够空间，也可以先 `resize`，再把 `copy` 的目标写成某个合法起点位置；或者直接使用容器成员函数 `insert`。但从通用性角度看，`copy + back_inserter` 是更标准、也更具有代表性的写法。

### 3.4 谓词与 `find_if`：把“条件”也变成参数

若只是按某个固定值查找，`find` 已经足够：

```cpp
find(begin, end, x);
```

它表示在区间 `[begin, end)` 中寻找值等于 `x` 的元素。若找到了，就返回指向该元素的迭代器；若没找到，就返回第二个参数，也就是 `end`。

但很多时候，程序想找的并不是“等于某个具体值”的元素，而是“满足某种条件”的第一个元素。例如，想在一段字符串中跳过前导空白，或者找到第一个不是空白符的字符。这时就需要更灵活的 `find_if`：

```cpp
i = find_if(i, str.end(), not_space);
j = find_if(i, str.end(), space);
```

这里第三个参数不再是一个值，而是一个能够回答“是或否”的函数。这样的函数通常称为**谓词**（predicate）。它的返回类型是布尔值，作用就是让算法在遍历元素时不断提问：“这个元素满足条件吗？”

例如：

```cpp
bool space(char c) {
    return isspace(c);
}

bool not_space(char c) {
    return !isspace(c);
}
```

然后就可以写出一个基于算法和迭代器的字符串分割函数。这个例子很有代表性，因为它说明：字符串处理并不一定要靠下标 `i`、`j` 一个个手动推进；很多时候，也可以用“找下一个满足条件的位置”这种更抽象的办法来写。

这里还顺便暴露出一个容易被忽略的问题：为什么不直接把 `isspace` 自己拿去当谓词？原因在于，`isspace` 本身属于重载函数家族。把重载函数名直接传给泛型算法时，编译器不一定能自动判断到底该选哪一个具体版本。因此，包一层简单的 `space(char)` 反而更清楚、更稳定。

从这里开始，读者应当建立一个新观念：算法的参数不只可以是“数据范围”，还可以是“处理规则”。而谓词，就是最常见的一类规则。

### 3.5 `transform`、`accumulate` 与“先变换，再统计”

除了查找和复制，另一个非常常见的需求是：把一段数据中的每个元素都变成另一个值，然后再对这些新值进行统计。例如，一批记录里每个对象都能计算出一个分数，那么完全可以先把这些分数提取出来，再对分数向量求中值。

这时就可以使用 `transform`：

```cpp
transform(students.begin(), students.end(),
          back_inserter(grades), grade_aux);
```

它的含义是：把区间中的每个元素依次交给转换函数 `grade_aux`，再把结果依次输出到目标位置中。这里“转换函数”本身又是一个参数，这进一步说明标准库算法有很强的组合性。只要某个动作能表达成“对每个元素做同一件事”，`transform` 往往就值得考虑。

若接下来还想把一段数值求和，则可以使用 `accumulate`：

```cpp
accumulate(v.begin(), v.end(), 0.0)
```

它定义在 `<numeric>` 中，作用是把区间中的元素从左到右依次累加。第三个参数是初值，同时它还决定了累加结果所使用的类型。比如这里写成 `0.0` 而不是 `0`，就是为了让整个累加过程按 `double` 类型来进行。

把 `transform` 和 `accumulate` 放在一起看，会看见一个更一般的程序组织模式：**先把复杂对象映射成某个更容易统计的值，再对这些值使用通用算法。** 这种“先变换、后汇总”的思路在实际程序中非常常见，也非常值得形成习惯。

例如，平均值函数可以写成：

```cpp
double average(const std::vector<double>& v)
{
    return accumulate(v.begin(), v.end(), 0.0) / v.size();
}
```

这就比手写一长段累加循环更直接，也更容易一眼看出意图：这里要做的是求总和，再除以元素个数。

### 3.6 删除、复制与分类

标准库中有一组名字看上去很像的算法：`remove_copy`、`remove_copy_if`、`remove_if`。初学时，它们非常容易混淆。

先看 `remove_copy`。它的意思并不是“把某些元素从原容器删掉”，而是“把不等于某个给定值的元素复制到别处”。例如：

```cpp
remove_copy(s.homework.begin(), s.homework.end(),
            back_inserter(nonzero), 0);
```

这句代码会把所有不等于 `0` 的作业分数复制到 `nonzero` 中。原来的 `homework` 并不会改变。而 `remove_copy_if` 只是把“删除依据”从某个具体值，推广成一个谓词条件而已。

真正更容易让人误解的是 `remove_if`。它的名字虽然带着 `remove`，但它本身**并不会改变容器大小**。它做的事情是：把所有“不应删除”的元素重新排到前面去，然后返回一个迭代器，指向“逻辑上的新结尾”。也就是说，算法操作的是元素次序，而不是容器长度。

因此，下面这句并不足以真正缩短向量：

```cpp
remove_if(students.begin(), students.end(), pgrade);
```

若想把“被挪到后面的那些无效元素”真正从容器里去掉，还必须再调用容器自己的 `erase`：

```cpp
students.erase(remove_if(students.begin(), students.end(), pgrade),
               students.end());
```

这就是非常经典的 **erase-remove 用法**。其中 `remove_if` 属于算法，作用在元素范围上；`erase` 属于容器成员函数，真正改变容器本身。把这两步合起来看，程序才真正完成“删除满足条件的元素”这一任务。

这里要牢牢记住一条很容易考、也很容易错的原则：**算法通常作用于容器中的元素，而不是容器本身。** 标准库之所以这样设计，正是为了保持算法的通用性。可一旦需要真正修改容器大小，就必须再由容器自己的成员函数出手。

### 3.7 `stable_partition`：一次遍历完成分类

有些任务的目标并不是单纯删除元素，而是把一批元素按照某个条件分成前后两组。例如，把满足条件的对象放前面，不满足条件的对象放后面，同时尽量保持相对顺序。此时就可以考虑 `stable_partition`。

典型形式如下：

```cpp
std::vector<Student_info>::iterator iter =
    stable_partition(students.begin(), students.end(), pgrade);
```

执行完成后，`iter` 会指向分界位置。也就是说，前半段是让谓词 `pgrade` 为真的元素，后半段是让谓词为假的元素。如果随后想把后半段单独取出来，就可以写：

```cpp
std::vector<Student_info> fail(iter, students.end());
students.erase(iter, students.end());
```

与前面“先 `remove_copy_if` 再 `remove_if`”那种两遍处理相比，`stable_partition` 更像是“一次性重新安排好元素，再沿着分界点切开”。这种写法很适合做分类问题，也帮助读者进一步理解：标准库算法提供的不只是最基础的“查找”和“复制”，还包含了许多更高层次的数据重组操作。

之所以特别强调这里的 `stable`，是因为它表示**稳定**。稳定的意思是：在同一组内部，元素原有的相对顺序尽量保持不变。这个性质在很多实际任务中都很有价值，因为程序往往并不希望为了分类而把原本已有的顺序全部打乱。

### 3.8 泛型函数：让函数摆脱具体类型

库算法之所以强大，一个重要原因是它们本身就是泛型的。所谓**泛型函数**，或者更准确地说**函数模板**（function template），就是一类不把数据类型写死，而是把“类型”本身也作为参数来抽象的函数定义方式。

例如，前面写过的 `median` 一开始可能只适用于 `vector<double>`：

```cpp
double median(std::vector<double> vec)
```

但若仔细观察就会发现，除了 `double` 以外，这个函数其实并没有依赖太多特殊知识。只要元素能比较大小、能排序、并且在偶数个元素时能做加法与除法，那么“求中值”的整体逻辑就同样成立。于是，就可以把它改写成模板：

```cpp
template <class T>
T median(std::vector<T> vec)
{
    typedef typename std::vector<T>::size_type vec_sz;
    vec_sz size = vec.size();
    if (size == 0)
        throw std::domain_error("median of an empty vector");
    std::sort(vec.begin(), vec.end());
    vec_sz mid = size / 2;
    return size % 2 == 0 ? (vec[mid] + vec[mid - 1]) / 2 : vec[mid];
}
```

这里的 `template <class T>` 表示：`T` 是一个类型参数，真正调用时再由编译器根据实参推导出具体类型。于是同一个 `median` 函数，就可以服务于 `vector<int>`、`vector<double>`，甚至在满足相关操作前提时服务于其他类型。

模板真正带来的力量，不是简单“少写几份重复代码”，而是让程序表达出一种更高层次的规律：这里关心的不是“某个具体类型怎么处理”，而是“凡是满足若干基本操作要求的类型，都可以按这一模式处理”。

模板第一次出现时，很多语法都容易让人感到陌生。其中最典型的一处就是：

```cpp
typedef typename std::vector<T>::size_type vec_sz;
```

这里的 `typename` 不能随便省略。原因在于，当编译器读到 `std::vector<T>::size_type` 时，仅从表面上还无法立刻确定它到底是一个类型名，还是别的成员名字。加上 `typename`，就是在明确告诉编译器：这里请把后面的东西当成类型来理解。

这是模板语法中非常典型的一条规则。它本身不复杂，但若完全不了解，就会觉得这句代码像是“突然多出来一个奇怪单词”。实际上，它只是为了消除模板语境中的歧义。

模板还有一个重要特点：它并不是普通函数那样“先单独编译出一个固定实体，再统一调用”。模板真正对应的具体函数版本，往往要等到程序使用它时，才会根据实参类型进行**实例化**（instantiation）。例如，第一次用 `median` 处理 `vector<double>`，就会得到一个以 `double` 为实际参数的版本；若后来又用它处理 `vector<int>`，则会再得到一个对应的新版本。

也正因为模板的具体实例往往在使用点附近才确定，所以许多环境都要求模板的**定义**而不只是声明，必须对使用它的编译单元可见。于是，模板函数常常直接写在头文件中，或者通过 `#include` 方式让定义一同被包含进来。这和普通函数“声明放头文件、定义放源文件”的习惯有明显不同，是模板使用时必须格外注意的地方。

### 3.9 五类迭代器与算法对能力的要求

到这里为止，读者已经多次看见“算法依赖迭代器能力”这句话。现在需要把这句话讲得更精确一些。并不是所有算法都对迭代器提出同样的要求。不同算法所需的操作不同，于是迭代器也可以按能力划分层次。

常见的五类迭代器可以概括为：

- 顺序只读访问
- 顺序只写访问
- 顺序读写访问
- 可逆访问
- 随机访问

名字虽然看上去有些长，但其实可以按“能做什么”来理解。最基础的是输入型或只读型：能向前走，能读当前位置的值。再往上一层是输出型或只写型：能向前走，能在当前位置写值。再往上，若既能读也能写，就能支持更多算法。若还能向后移动，就是可逆访问。若不仅能前后走，还能做 `iter + n`、`iter - n` 这类跳跃式运算，那就是随机访问。

不同算法正是依赖这些能力来工作。例如：

```cpp
template <class In, class X>
In find(In begin, In end, const X& x)
{
    while (begin != end && *begin != x)
        ++begin;
    return begin;
}
```

这个 `find` 只要求顺序只读访问，因为它只需要比较当前元素，再不断前进。又例如：

```cpp
template <class In, class Out>
Out copy(In begin, In end, Out dest)
{
    while (begin != end)
        *dest++ = *begin++;
    return dest;
}
```

这里输入范围只要求能读，输出位置只要求能写。

再看 `replace`：

```cpp
template <class For, class X>
void replace(For begin, For end, const X& x, const X& y)
{
    while (begin != end) {
        if (*begin == x)
            *begin = y;
        ++begin;
    }
}
```

它既要读当前位置的值，又可能把它改成新的值，因此至少需要顺序读写访问。

`reverse` 则更进一步：

```cpp
template <class Bi>
void reverse(Bi begin, Bi end)
{
    while (begin != end) {
        --end;
        if (begin != end)
            swap(*begin++, *end);
    }
}
```

因为它不仅要从前往后走，还要从后往前退，所以至少需要可逆访问。

最后像二分查找这样的算法：

```cpp
template <class Ran, class X>
bool binary_search(Ran begin, Ran end, const X& x)
{
    while (begin < end) {
        Ran mid = begin + (end - begin) / 2;
        if (x < *mid)
            end = mid;
        else if (x > *mid)
            begin = mid + 1;
        else
            return true;
    }
    return false;
}
```

这里已经明显使用了 `+`、`-` 和大小比较，因此必须依赖随机访问迭代器。

这些模板函数的例子，现在可以把它们放在一起看。它们的共同特征是：函数体里面几乎没有出现任何“具体容器”或“具体元素类型”的信息，出现的只是“迭代器能否解引用”“元素能否比较”“位置能否前进或后退”这类更基础的操作。

这正是泛型编程最核心的思想。它关心的不是“这是一个 `vector<int>` 还是 `list<string>`”，而是“传进来的这两个参数，是否像某种合格的迭代器一样工作；传进来的元素，是否支持某些必要操作”。一旦这些前提满足，算法就可以成立。

因此，泛型函数和普通函数最大的区别，不是多了 `template` 这几个字符，而是抽象层次更高了。普通函数往往在说“对这种具体数据该怎么做”，而泛型函数说的是“凡是具备这些能力的数据，都可以这么做”。

### 3.10 Lambda：把小规则直接写在算法旁边

前面多次提到谓词和转换函数。若这些函数非常短，而且只在一个地方用一次，那么专门去写一个具名函数，有时反而显得啰嗦。C++ 为此提供了 **Lambda 函数**，也就是匿名函数。

基本形式如下：

```cpp
[捕获列表](参数列表) -> 返回类型 {
    函数体
}
```

例如：

```cpp
auto add = [](int x, int y) -> int {
    return x + y;
};
```

它的本质是：现场定义一个小函数对象，并把它存到变量 `add` 中。真正让 Lambda 大放异彩的地方，是把它直接当作算法参数传进去。例如排序时，若比较规则非常简单，就可以写成：

```cpp
std::sort(numbers.begin(), numbers.end(),
          [](int a, int b) { return a < b; });
```

这样一来，“怎么比较”这个规则就直接写在算法旁边，程序读起来会很连贯。

Lambda 里的**捕获列表**也非常重要。它决定了这个匿名函数能否访问外部作用域中的变量，以及是按值访问还是按引用访问。常见写法包括 `[=]`、`[&]`、`[x]`、`[&y]` 等。若只是初学阶段，至少应当先记住两层意思：第一，Lambda 并不总是完全独立的，它可以借用外部变量；第二，借用时要明确是复制一份值，还是直接引用原变量。

在较新的标准中，还可以写出**泛型 Lambda**：

```cpp
auto add = [](auto x, auto y) {
    return x + y;
};
```

这时参数类型同样交给编译器自动推导，于是 Lambda 也能体现出模板式的通用性。若编译环境支持 C++14 及以上标准，这种写法会非常方便。不过从学习顺序上看，仍然应当先把“普通 Lambda 本质上是一个匿名函数对象”这件事理解清楚，再去接受“参数也可以自动推导”这一层扩展。

### 3.11 本章小结

这一章的核心任务，是把“程序如何处理数据”进一步抽象化。标准库算法告诉我们，许多常见处理过程其实不需要每次重写循环，只要给出范围和规则，就能直接复用现成算法。迭代器让算法摆脱了对具体容器的依赖，从而获得数据结构独立性。谓词和适配器又使算法参数不再只是数据本身，还可以包括判断规则和插入方式。进一步地，模板函数把“具体类型”也抽象成了参数，使函数从处理一种类型，扩展到处理一大类满足共同条件的类型。最后，Lambda 又让局部的小规则可以直接写在算法旁边，使程序更紧凑、更自然。

如果说前两章解决的是“怎样把程序写清楚”，那么这一章进一步解决的是：**怎样把已经写清楚的程序，再写得更通用、更可复用。**

### 本章小练习

1. 选择题  
下面关于 `remove_if` 的说法，正确的是（ ）

A. 它会直接缩短 `vector` 的长度  
B. 它会删除满足条件的元素，并释放对应内存  
C. 它会重新排列元素，并返回逻辑新结尾的位置  
D. 它只能用于 `list`，不能用于 `vector`

2. 程序填空题  
设 `std::vector<int> src = {1, 2, 3};`，`std::vector<int> dst;`。现在希望把 `src` 中所有元素追加到 `dst` 末尾。请补全下面语句中的空白部分：

```cpp
copy(src.begin(), src.end(), ____________________);
```

### 参考解答

1. 正确答案是 `C`。  
`remove_if` 属于算法，它处理的是区间中的元素排列，而不是容器大小本身。执行后，未被“删除”的元素会被移到前面，并返回新的逻辑结尾位置。若想真正缩短容器，还需要再配合容器自己的 `erase`。

2. 可以填

```cpp
back_inserter(dst)
```

补全后为：

```cpp
copy(src.begin(), src.end(), back_inserter(dst));
```

因为 `dst` 一开始是空的，不能把 `dst.end()` 直接当成一段已分配好的写入区间。`back_inserter(dst)` 会把复制动作转化为不断调用 `dst.push_back(...)`。

## 第四章 类与对象的第一步

### 本章概要

前面几章已经逐渐让程序摆脱了“所有数据都散着放、所有逻辑都直接写在主函数里”的初级状态。字符串被封装成了 `string`，批量数据交给了 `vector`，许多重复处理也交给了函数、算法和模板。走到这里，读者自然会遇到一个更关键的问题：如果程序里有一种数据本身就代表一个完整的对象，例如一个学生、一门课程、一条记录、一个图形，那么这些数据和与之相关的操作，能不能进一步收拢到一起，而不是继续分散地暴露在程序各处？

这正是类（class）要解决的问题。本章的重点不是“背几个类的语法”，而是理解为什么程序需要自定义类型，以及类如何把接口和实现分开、把数据和操作放在一起、把对象的状态维护得更可靠。围绕这一主线，本章会介绍成员函数、`const` 成员函数、访问控制、访问器函数、封装、`struct` 与 `class` 的区别，以及构造函数、初始化列表、对象初始化顺序等内容。读完这一章后，读者应当能够从“把若干数据放进一个结构体”进一步走向“设计一个更像样的类”，并理解类的真正意义并不只是语法形式，而是**控制对象该如何被使用**。

### 4.1 定义新类型

在 C++ 中，最基础的数据类型属于语言核心的一部分，例如 `char`、`int`、`double`。这些类型由语言直接提供，使用方式固定而明确。与此同时，标准库又提供了许多更复杂但同样常用的类型，例如 `string`、`vector`、`istream`。程序员在使用这些类型时，往往已经不会把它们当成“某些底层细节的组合”，而是直接把它们当成可以自然操作的对象。

这恰好体现了 C++ 很重要的一种思想：**程序员也可以定义自己的类型，并尽量让它们像内置类型一样自然地使用。** 例如，一个“学生信息”显然不只是几个互不相关的变量凑在一起。它天然就是一种独立对象，应该有自己的状态，也应该有与这个状态配套的操作。若程序始终把这些内容拆散着用，随着规模增大，很多问题就会越来越明显。

最朴素的写法可能是：

```cpp
struct Student_info {
    std::string name;
    double midterm, final;
    std::vector<double> homework;
};
```

这种写法当然已经比“分别维护三四个独立变量”更进一步了，因为它至少把一条记录打包成了一个整体。但它仍然存在明显缺点。第一，任何使用这个类型的人都可以直接接触并改动它的所有成员，于是对象状态很难被严格控制。第二，若输入失败或对象尚未初始化完成，调用者很容易在不了解细节的情况下误用这些成员。第三，与这个对象相关的操作，例如读取、求成绩、比较大小、判断有效性等，仍然分散在类外部，接口并不集中。

因此，定义新类型的真正意义，并不是把若干变量换个壳子装起来，而是让程序开始明确地区分：**哪些东西属于对象的内部实现，哪些东西应当作为对象对外公开的接口。**

### 4.2 从结构体到类：接口与实现的分离

若只使用我们之前学过的 `struct` 的最朴素写法，那么调用者会直接写出：

```cpp
record.name
record.midterm
record.homework
```

这意味着外部代码必须了解对象内部到底有哪些成员、它们叫什么名字、应该怎么组合使用。若以后内部表示方式改变，例如把姓名成员从 `name` 改成 `n`，或者把作业成绩的保存方式换掉，所有直接访问这些成员的外部代码都可能跟着出问题。

类的出现，正是为了把这种“实现细节四处泄露”的局面收起来。理想状态下，用户只应该通过一个清楚、稳定的接口来使用对象，而不必知道它内部到底如何存储。这种“把接口与实现细节分离开来”的思想，就是**封装**（encapsulation）的核心。

例如，与学生信息相关的“读取”和“求成绩”可以不再写成独立函数，而是放回到对象内部，变成成员函数。于是，对象不再只是一个被动的数据包，而变成了一个既保存状态、又知道该如何操作自身状态的实体。这样的设计一方面减少了外部代码对内部细节的依赖，另一方面也让对象的使用方式更统一、更自然。

因此，在真正开始写类之前，最重要的不是先记语法，而是先转变一个观念：**类不是“更复杂的结构体”，而是一个明确划分接口与实现边界的用户自定义类型。**

### 4.3 成员函数：对象自己的操作

如果某个函数本来就必须围绕某个对象的内部数据来工作，那么把它写成成员函数往往更合适。典型例子是“读取一条记录”：

```cpp
std::istream& Student_info::read(std::istream& in)
{
    in >> name >> midterm >> final;
    read_hw(in, homework);
    return in;
}
```

这里函数名前面的 `Student_info::` 非常重要，它表示这个函数属于 `Student_info` 类。也就是说，`read` 不再是一个对所有对象一视同仁的普通函数，而是“学生信息对象自己的读取操作”。

成员函数与普通函数最直观的区别在于：调用方式不同。普通函数会写成

```cpp
read(cin, record);
```

而成员函数写成

```cpp
record.read(cin);
```

这种写法更贴近人的思维方式，因为程序明确表达了“让 `record` 自己从输入流里读入内容”。同时，在成员函数体内部，也不再需要通过 `s.name`、`s.midterm` 这样的形式访问成员，而是可以直接写 `name`、`midterm`、`homework`。这是因为成员函数天然就是在某个具体对象的上下文里执行的。

从设计角度看，成员函数最大的好处是让“这个操作到底作用于谁”变得非常清晰。对象不再是一个被外部函数任意摆弄的原材料，而是一个拥有自身接口的实体。

当一个成员函数只是读取对象中的数据，而不应当修改对象状态时，就应该把它声明为 `const` 成员函数。例如：

```cpp
double Student_info::grade() const
{
    return ::grade(midterm, final, homework);
}
```

这里参数列表后面的 `const` 不是装饰性的写法，而是一项明确承诺：调用这个函数不会改变当前对象的内部状态。换句话说，它只是“读取并计算”，而不会把对象改成新的样子。

这件事的重要性远远超过表面语法。第一，它能帮助读代码的人迅速判断一个成员函数的性质。看到 `const`，就知道这个函数是只读的。第二，它让编译器也能参与检查。若程序员在 `const` 成员函数内部试图修改数据成员，编译器会报错。第三，它直接关系到 `const` 对象的可用性：**`const` 对象只能调用 `const` 成员函数**。

这一条规则非常关键。假设有一个只读对象，若它竟然可以调用一个可能修改自身状态的成员函数，那么“只读”这个承诺就被破坏了。因此，只有那些确实不会改动对象状态的操作，才应该被标记为 `const` 成员函数。

代码中还有一个小细节也值得解释：

```cpp
return ::grade(midterm, final, homework);
```

这里 `::grade` 前面的 `::` 表示使用全局作用域中的那个 `grade`，而不是某个对象成员版本。也就是说，在类内部调用时，程序员有时仍然需要明确指定“我要的到底是成员函数，还是类外的普通函数”。这类写法虽然不算复杂，但在阅读代码时必须认出来。

### 4.4 访问控制：`public`、`private` 与 `protected`

类之所以能真正起到封装作用，关键在于它不是简单把函数和数据摆在一起，而是还提供了**访问控制**。访问控制由保护标签来完成，最常见的是 `public`、`private`，此外还有 `protected`。

最典型的写法如下：

```cpp
class Student_info {
public:
    double grade() const;
    std::istream& read(std::istream&);

private:
    std::string name;
    double midterm, final;
    std::vector<double> homework;
};
```

其中，`public` 下的成员是对外公开的接口，任何使用这个类的人都可以访问；`private` 下的成员则只允许这个类自己的成员函数访问，外部用户不能直接碰；`protected` 则主要留给后续继承场景使用，本章只需要先知道它也是一种访问控制标签即可。

这几种标签的真正意义，并不只是“语法上能不能访问”。更深一层的含义是：程序设计者正在明确告诉使用者，“哪些操作是你应该使用的，哪些细节不是你应该直接碰的”。一旦类把核心数据放到 `private` 部分，外部代码就不再能随手改动对象内部状态。这样一来，对象的正确性就更容易被类自身维护。

还要注意一点：在同一个类中，保护标签可以出现多次，也不要求固定顺序。它们的作用只是把后面的成员归入对应访问级别，因此理解它们的语义，比记住格式细节更重要。

### 4.5 `struct` 与 `class` 的真正区别

很多初学者第一次接触类时都会问：既然前面已经有 `struct`，那为什么还要再学 `class`？答案其实比想象中简单。**在 C++ 中，`struct` 和 `class` 的核心机制几乎一样，最本质的区别只是默认访问级别不同。**

对于 `struct`，默认访问级别是 `public`；对于 `class`，默认访问级别是 `private`。例如：

```cpp
struct A {
    int x;   // 默认 public
};

class B {
    int x;   // 默认 private
};
```

这意味着，单从语言能力来说，`struct` 完全也可以写成员函数、写 `private`、写构造函数；`class` 也完全可以通过显式写出 `public:` 来暴露接口。因此，两者不是“一个弱、一个强”的关系，而更像两种风格不同的默认起点。

在实际写作习惯上，人们常常把 `struct` 用于表示较简单、较直接的数据聚合，把 `class` 用于表示更强调封装和接口控制的类型。但这是一种设计习惯，而不是语法上的铁律。真正重要的是：**只要一个类型开始承担“隐藏实现、控制访问、维护对象状态”的职责，那么它就更适合作为类来设计。**

### 4.6 访问器函数与内联函数

一旦把数据成员放进 `private`，外部代码就不能再直接写 `record.name` 了。但这并不意味着这些信息永远不能被读取。更合理的做法，是通过一个小而清楚的接口把它们暴露出来，例如：

```cpp
std::string name() const { return n; }
```

这样的函数通常叫作**访问器函数**（accessor）。它的作用是允许外部读取某些内部数据，但又不把内部表示方式直接暴露出去。调用者只知道“对象有一个可读的名字”，却不必知道这个名字到底保存在成员 `name` 里、成员 `n` 里，还是将来换成别的结构里。

访问器的重要意义在于，它让类能够在“完全封闭”和“完全裸露”之间找到一个平衡。对象不是把一切都暴露给外部，但也不是把一切都藏得死死的；它会通过少量精心设计的接口，让外部获取确实需要知道的信息。

这类很短的小函数，常常直接写在类定义内部。写在类定义内部的成员函数通常会被当作**内联函数**（inline function）处理。例如：

```cpp
class Student_info {
public:
    std::string name() const { return n; }
private:
    std::string n;
};
```

编译器在处理内联函数时，往往会尝试把函数调用直接替换成函数体本身，从而减少普通函数调用的开销。对初学者来说，更值得抓住的不是性能细节，而是使用场景：**那些非常短小、语义清楚的成员函数，常常适合直接写在类定义中。**

### 4.7 某些函数不一定要写成成员

看到类以后，很多人会本能地觉得：凡是和这个类有关的函数，都应该写成成员函数。其实并不是这样。一个较常见、也较可靠的判断原则是：**如果一个函数需要改变对象状态，或者必须深度依赖对象内部表示，那么它通常适合做成员函数；如果一个函数只是把几个对象拿来做对称比较，那么它未必需要成为成员。**

例如，`read` 显然应当是成员函数，因为它会改变对象状态；`grade` 也很适合做成员函数，因为它直接围绕对象内部数据来工作。但比较两个学生姓名大小的函数：

```cpp
bool compare(const Student_info& x, const Student_info& y)
{
    return x.name() < y.name();
}
```

通常就更适合作为**非成员函数**。原因在于，它并不偏向某一个对象，而是在两个对象之间进行对称比较。把它写成成员函数反而容易显得别扭，因为“比较谁和谁”并不天然属于某一个对象内部要负责的事。

这个判断原则以后会越来越重要，尤其到了运算符重载那里更会反复出现。当前阶段只需先形成一个清楚观念：类并不是要把所有相关函数一股脑塞进去，而是要合理划分“对象自己的操作”和“类外辅助操作”。

### 4.8 对象有效性

如果一个对象刚被默认创建出来，却还没有真正读入有效数据，那么直接拿它去求成绩，很可能会产生意外。例如：

```cpp
Student_info s;
cout << s.grade() << endl;
```

这里的问题并不在于语法，而在于对象状态是否真的“准备好了”。若作业向量为空，求成绩时就可能触发异常。最粗暴的应对办法当然是让外部代码自己检查 `homework` 是否为空，但这样做会立刻破坏封装，因为外部开始依赖对象内部细节。

更合理的做法，是由类自己提供一个明确接口来说明对象是否处于有效状态，例如：

```cpp
bool valid() const { return !homework.empty(); }
```

这里的 `valid()` 并不是在暴露对象内部细节，而是在暴露一个更高层次、更适合外部理解的事实：这个对象当前是否包含足够有效的数据。外部代码只需要知道“对象是否可用”，而不需要知道“它具体通过什么内部条件判断可用”。

这正是封装真正发挥作用的地方。封装并不是把数据一锁了之，而是在“哪些信息对外应该稳定”“哪些实现细节可以留在内部”之间划出界线。接口一旦设计得好，内部实现就可以在不影响使用者的情况下慢慢调整，这就是类比单纯结构体更有长期价值的原因。

### 4.9 构造函数：对象在诞生时就应当处于合理状态

有了封装之后，类设计者就不仅要关心对象“如何被使用”，还必须关心对象“从一开始如何被初始化”。这正是**构造函数**（constructor）的职责。

构造函数是一类特殊的成员函数，它的名字与类名相同，没有返回值。当创建一个对象时，系统会自动调用合适的构造函数来完成初始化。一个类可以拥有多个构造函数，只要它们的参数个数或类型不同。例如：

```cpp
class Student_info {
public:
    Student_info();
    Student_info(std::istream&);
};
```

上述的两种构造函数分别对应两种不同的对象创建方式。前者调用默认构造函数，创建一个“暂时还没有读入记录”的对象；后者则使用输入流构造对象，表示对象在创建时就顺便读入了一条记录。

接下来，我们就分别来讨论这两种构造函数。

不带参数的构造函数通常叫作**默认构造函数**。它最基本的任务，是在没有额外输入信息时，也把对象初始化成一个合理、可解释的状态。例如，对学生信息来说，一个很自然的默认状态是：姓名为空字符串，作业向量为空，期中和期末成绩设为 `0`。

典型写法如下：

```cpp
Student_info::Student_info() : midterm(0), final(0) {}
```

这里冒号后面的部分叫作**构造函数初始化列表**（initializer list）。它由若干个 `成员名(初值)` 组成，用来在对象真正构造时直接初始化数据成员。

初学者很容易把“初始化”和“在构造函数体内赋值”混为一谈。例如，也许有人会写：

```cpp
Student_info::Student_info() {
    midterm = 0;
    final = 0;
}
```

这在很多情况下也能工作，但从机制上说，它和初始化列表并不完全相同。初始化列表是在对象成员被创建时就直接赋予初值；而函数体内赋值通常意味着成员已经先经历了一次默认初始化，然后又被重新赋值。对于复杂成员来说，这可能造成多余工作。因此，只要某个成员的初值在构造时就已确定，通常优先考虑写入初始化列表中。

除了默认构造函数之外，类也常常需要**带参数的构造函数**。例如：

```cpp
Student_info::Student_info(std::istream& is)
{
    read(is);
}
```

这个构造函数的含义很清楚：对象创建出来之后，立刻通过 `read` 从输入流中读入内容。虽然函数体看起来很短，但它体现了一个更一般的设计习惯：**若对象的某种初始化方式本身就很常见，那么应当把它直接做成构造函数，而不是要求用户先默认构造、再额外手动调用若干步骤。**

从程序运行角度看，创建一个对象时通常会经历这样几个阶段。首先，系统为对象分配内存。然后，根据构造函数的初始化列表初始化各个数据成员。最后，再执行构造函数体中的语句。理解这个顺序非常重要，因为它说明：成员的初始化发生在函数体执行之前。

也正因为如此，构造函数体内的代码并不是“从无到有地造出成员”，而是在成员已经被初始化之后，再做进一步工作。

### 4.10 初始化顺序与默认初始化

构造函数有一个特别容易被忽视、但非常重要的细节：**成员的初始化顺序由它们在类中声明的顺序决定，而不是由初始化列表中书写的顺序决定。** 这意味着，若一个成员的初始化依赖另一个成员，就必须非常小心。

例如，若类中先声明 `a`，再声明 `b`，那么无论初始化列表里把谁写在前面，真正初始化时仍然总是先初始化 `a`，再初始化 `b`。因此，如果一个成员要依赖另一个成员来决定初值，最安全的做法往往是重新调整声明顺序，或者在构造函数体内再进行赋值，而不是在初始化列表里冒险依赖尚未稳定的成员。

此外，还要知道“默认初始化”和“值初始化”并不完全一样。若一个类没有自己定义构造函数，那么成员的初始化会递归地交给它们自己的类型处理。对于类类型成员来说，通常会调用相应默认构造；但对于内置类型成员来说，默认初始化未必会自动把它们清零，值初始化才会明确给出零值。正因为这些规则并不总是直观，编写类时更应该遵循前面的基本习惯：**尽量显式地把关键成员初始化清楚，而不要依赖模糊的默认行为。**

### 4.11 本章小结

这一章真正建立起来的，是从“数据结构”走向“类型设计”的第一步。类让程序员可以定义新的类型，并把数据和操作统一组织起来。成员函数让对象拥有自己的接口；`const` 成员函数进一步区分了“只读操作”和“可能改状态的操作”；访问控制让外部代码不再任意触碰内部细节；访问器函数和非成员辅助函数则帮助类在封装和可用性之间取得平衡。构造函数则把关注点进一步推进到对象诞生的那一刻，要求对象从创建开始就尽量处于合理、稳定的状态。

如果说前几章主要是在学习“如何更好地使用已有的类型和工具”，那么这一章开始，程序员已经真正迈入了“如何设计自己的类型”这一层次。后面所有更深入的内容，例如运算符重载、继承、多态和资源管理，都会建立在这一层基础之上。

### 本章小练习

1. 程序阅读题  
阅读下面程序，写出输出结果，并简要说明原因。

```cpp
#include <iostream>
#include <string>
using namespace std;

class Book {
public:
    Book(): title("None"), price(0) {}
    Book(const string& s, double p): title(s), price(p) {}
    string name() const { return title; }
    double cost() const { return price; }

private:
    string title;
    double price;
};

int main() {
    Book a;
    Book b("C++", 36.5);
    cout << a.name() << " " << a.cost() << endl;
    cout << b.name() << " " << b.cost() << endl;
    return 0;
}
```

### 参考解答

1. 输出为

```text
None 0
C++ 36.5
```

原因是对象 `a` 调用了默认构造函数，因此标题被初始化为 `"None"`，价格被初始化为 `0`；对象 `b` 调用了带参数构造函数，因此标题和价格分别初始化为 `"C++"` 与 `36.5`。随后输出调用的是访问器函数 `name()` 和 `cost()`，它们都只是返回成员值，并不改变对象状态。

## 第五章 模板类与资源管理的起点

### 本章概要

前面已经学过函数模板，也已经知道“某种处理逻辑”可以不依赖某一种具体类型来写。接下来，自然会出现一个更进一步的问题：如果不仅是函数可以泛型化，连一个完整的类也希望适用于多种类型，那么该怎么做？例如，前面经常使用标准库中的 `vector<int>`、`vector<double>`、`vector<Student_info>`。它们本质上是同一个容器思想，只是其中存放的元素类型不同。这样的问题，就会把我们带到**模板类**（class template）的世界。

但这一章并不只是讲模板语法。课题一旦从“使用已有容器”转到“自己实现一个类似容器的类”，程序员就必须面对更现实也更棘手的问题：对象中如果含有动态申请的内存，那么复制、赋值和销毁到底该怎么处理？默认行为是否还可靠？什么时候该用 `new` 和 `delete`，什么时候又要把“申请空间”和“构造对象”分开？这些问题表面上看像是实现细节，实际上却直接决定一个类是否安全、是否高效、是否能像内置类型一样自然使用。

因此，这一章的核心主线其实有两条。第一条是模板类：如何把一个具体类推广为适用于多种元素类型的类。第二条是资源管理：一个管理动态内存的类，为什么必须认真处理构造、复制、赋值和析构。围绕这两条主线，本章会引入 `Vec<T>` 这一典型例子，并系统讨论类型别名、下标运算符、迭代器接口、复制控制、`explicit`、动态扩容以及 `allocator` 等内容。

### 5.1 从函数模板走向类模板：`Vec<T>`

在上一章里，模板函数已经说明了一件事：若多个函数之间的差别只在于操作的类型不同，那么可以把“类型”本身也抽象成参数。类模板其实沿着同样的思路继续向前走。若多个类之间的结构完全相同，只是其中某个成员类型、返回值类型或接口中的类型不同，那么完全可以把这个类也写成模板。

最常见、也最直观的例子就是向量类。无论容器中存的是整数、字符串，还是自定义的学生信息对象，容器本身都需要支持相似的操作：保存一批元素、报告大小、按下标访问、返回首尾迭代器、支持复制、赋值和销毁。既然这些行为在不同元素类型下都几乎一致，那么把整个类写成模板，就是非常自然的选择。

模板类最基本的形式如下：

```cpp
template <class T>
class Vec {
public:
    // 接口

private:
    T* data;
    T* limit;
};
```

这里的 `T` 就是类型参数。以后写 `Vec<int>`，表示元素类型取为 `int`；写 `Vec<std::string>`，表示元素类型取为 `std::string`。也就是说，模板类不是一个“已经确定好的类”，而更像是一份“类的生成规则”。只有当程序真的写出 `Vec<int>` 或 `Vec<Student_info>` 这样的具体使用形式时，编译器才会为相应类型生成具体版本。

那么，初学者容易产生的疑问是：标准库已经提供了很好用的 `vector`，那么为什么还要自己实现一个 `Vec<T>`？答案并不是因为标准库不够好，而是因为这个例子非常适合把多个核心知识点串在一起。

一个看似简单的向量类，实际上会同时触及模板类、动态内存、下标运算符、迭代器接口、复制构造函数、赋值运算符、析构函数、扩容策略以及对象构造与空间分配的区别。换句话说，`Vec<T>` 不是为了替代标准库，而是为了让程序员真正看见：一个“像 `vector` 一样自然可用的类”背后，到底需要做多少设计和保障。

例如，一个最简化的 `Vec<T>` 至少要知道自己管理的是哪一段内存。在上面的例子中，`data` 指向首元素位置，`limit` 指向尾后位置。这样只要做一个指针差，就能得到元素个数。后来为了支持动态增长，还会再多出一个 `avail`，表示“当前已构造元素的尾后位置”，而 `limit` 则转而表示“当前整块已分配空间的尾后位置”。于是，容器的状态会变成：

- `data`：已分配空间的起点  
- `avail`：已经真正放入元素后的尾后位置  
- `limit`：整块可用空间的尾后位置

这组设计很值得重视，因为它让“已经占用的部分”和“尚未使用但已分配的部分”被区分开来。也正是从这里开始，程序员真正进入“资源类”设计的领域。

### 5.2 模板类的成员定义与作用域中的 `T`

模板类和普通类有一个非常显眼的区别：在类的作用域外定义成员函数时，类名本身往往也要带上模板参数。例如：

```cpp
template <class T>
Vec<T>& Vec<T>::operator=(const Vec& rhs)
{
    // ...
}
```

这里之所以要同时写出 `template <class T>` 和 `Vec<T>::`，原因很直接：类本身并不是单一的 `Vec`，而是一整族 `Vec<T>`。离开类定义内部之后，编译器已经不知道这里说的是哪一个具体模板类作用域，因此必须把模板参数补出来。

同样地，在类作用域内部，很多类型名不必重复写完整限定。例如在类体中可以直接写 `iterator`、`size_type`；但到了类外定义成员函数时，就必须明确告诉编译器它们来自哪一个模板实例的作用域，比如 `iterator` 需要写成 `Vec<T>::iterator`。

这类写法看起来啰嗦，实则非常有逻辑：模板参数一旦离开类体，就不能再被默认省略。

### 5.3 `new`、`delete` 与 `malloc`、`free` 的本质差别

一旦自己实现容器类，就必须考虑如何申请和释放内存。最直接想到的工具往往是 `new` 和 `delete`。例如：

```cpp
T* ptr = new T;
// ...
delete ptr;
```

若是数组形式，则写成：

```cpp
T* arrayPtr = new T[100];
// ...
delete[] arrayPtr;
```

这里一定要注意单对象和数组对象的释放形式不同：`new T` 对应 `delete ptr`，`new T[n]` 对应 `delete[] ptr`。这不是纯语法细节，而是因为数组版本可能要逐个调用多个元素的析构函数，释放策略本来就不同。

许多读者学过 C 语言后，往往会自然而然地把 `new/delete` 与 `malloc/free` 对照起来。二者确实都与堆空间有关，但本质并不相同。`malloc` 和 `free` 只负责按字节申请与释放原始内存；而 `new` 与 `delete` 除了处理内存以外，还会负责对象的构造和析构。若 `T` 是一个类类型，那么 `new T` 不只是“挪来一块空间”，还意味着“在这块空间上真正构造一个对象”；对应地，`delete` 也不只是“把空间还回去”，而是会先调用析构函数，再回收内存。

因此，若把这两组工具简单看成“新旧两种写法”，就会漏掉最关键的一层：**C++ 中内存与对象并不是完全等同的概念。** 有时程序需要的不是“立刻造出一排对象”，而只是“先拿到一块尚未构造对象的原始空间”，这就会引出后面更精细的内存管理方式。

这样也并非说我们可以总写 `new T[n]`。实际上，很多时候 `new T[n]` 并不是最合适。若目标只是快速做出一个“固定大小、元素都有默认值”的容器，那么 `new T[n]` 看上去很方便。但它有一个明显限制：它要求元素类型 `T` 能被默认构造。若 `T` 没有默认构造函数，或者默认构造的代价很大，那么这种做法就会变得不够灵活、也不够高效。

这正是我们强调要把内存申请释放和对象构造析构分离开来的原因。很多时候，程序真正想要的是：

1. 先申请一块足够大的原始内存；  
2. 只在真正需要的位置构造对象；  
3. 只析构那些真正被构造过的对象；  
4. 最后统一释放整块内存。

这种做法比直接 `new T[n]` 更细致，也更接近标准库容器的真实思路。它让类不仅能管理“有多少元素”，还能管理“已经分配了多少空间”，从而为之后的动态扩容打下基础。

也正因如此，在后面，我们会引入 `allocator` 以及 `uninitialized_copy`、`uninitialized_fill` 这类工具。它们存在的根本原因，并不是为了把代码写得更玄乎，而是为了精细地区分：**空间是否已经分配**，与**对象是否已经在这块空间上被构造出来**，其实是两件不同的事。

### 5.4 构造函数与 `explicit`

一个像向量这样的类，至少应当支持几种基本构造方式。常见的有三类：

1. 默认构造一个空向量；  
2. 给定元素个数，构造一个固定大小的向量；  
3. 给定元素个数和初始值，构造一个每个元素都相同的向量。

典型接口可以写成：

```cpp
Vec() { create(); }
explicit Vec(std::size_t n, const T& val = T()) { create(n, val); }
```

这里第二个构造函数前面的 `explicit` 很重要。它表示这个单参数构造函数不能被编译器拿去做隐式转换。例如：

```cpp
Vec<int> vi(100);   // 合法
Vec<int> vi = 100;  // 不希望成立
```

若没有 `explicit`，某些单参数构造函数可能会在程序员没有明确要求的地方被自动调用，从而把原本只是一个数字的表达式悄悄变成一个对象。这类隐式转换有时很方便，但在容器类这类语义较强的类型中，往往更容易制造歧义。因此，我们专门强调 `explicit`：**它的作用不是让构造函数更“严格”，而是防止不必要的隐式构造。**

对初学者来说，理解这一点比死记规则更重要。凡是单参数构造函数，只要不希望它被当作类型转换入口，就应认真考虑是否加上 `explicit`。

### 5.5 类型别名、下标与迭代器接口

一个“像标准容器一样好用”的类，不只是要能存数据，还要提供一套用户习惯的类型名与操作接口。例如：

```cpp
template <class T>
class Vec {
public:
    typedef T* iterator;
    typedef const T* const_iterator;
    typedef std::size_t size_type;
    typedef T value_type;
    typedef T& reference;
    typedef const T& const_reference;
    // ...
};
```

这些类型别名（type alias）看起来像细节，实际上很重要。它们让使用者不必知道实现细节，就能用统一名称来描述“迭代器类型”“元素类型”“下标类型”“引用类型”等信息。这正是抽象数据类型的一个关键特征：**接口应该暴露概念，而不是暴露底层写法。**

接着，类还应当提供最基本的容器操作。例如大小与下标：

```cpp
template <class T>
typename Vec<T>::size_type Vec<T>::size() const
{
    return avail - data;
}

template <class T>
T& Vec<T>::operator[](size_type i)
{
    return data[i];
}

template <class T>
const T& Vec<T>::operator[](size_type i) const
{
    return data[i];
}
```

这里有几个点需要一起看。第一，`size()` 是一个 `const` 成员函数，因为它只读取容器状态。第二，下标运算符通常要提供两个版本：一个用于非常量对象，返回可修改引用；另一个用于常量对象，返回只读引用。第三，这里再次出现了类外模板成员定义里的 `typename`，因为 `Vec<T>::size_type` 属于依赖模板参数的类型名。

容器类还应提供 `begin()` 和 `end()`，同样往往要分常量与非常量两个版本：

```cpp
iterator begin() { return data; }
const_iterator begin() const { return data; }

iterator end() { return avail; }
const_iterator end() const { return avail; }
```

这样一来，`Vec<T>` 的使用方式就开始接近标准库容器了。也就是说，模板类的目标并不只是“能工作”，而是尽量提供与现有容器一致的接口习惯。

### 5.6 复制控制：复制，赋值与析构

一旦类内部管理了动态资源，问题就会立刻变得比普通类复杂得多。假设一个向量类内部有指针成员指向堆空间，那么对象被复制、赋值或销毁时，程序就不能再简单依赖编译器自动生成的默认行为。否则，多份对象可能会指向同一块内存，最终导致重复释放、悬空指针或资源泄漏。

这就是我们所强调的**复制控制**（copy control）。一般来说，类可以控制对象在创建、复制、赋值和销毁时的行为；而一旦一个类在构造时申请了资源，它几乎就必须认真考虑三件事：复制构造函数，赋值运算符与析构函数。

这三者常常被并称为“规则中的三件套”，更常见的口头说法是**三者缺一不可的规则**。理由很直接：如果一个类需要析构函数去释放资源，那么默认复制和默认赋值往往就已经不再安全；若复制和赋值都需要特殊处理，那么析构也不可能完全无关。

这条规则非常值得牢牢记住。它不是某种死记硬背的口诀，而是资源管理逻辑的自然结果。只要类拥有动态资源，就应当立刻追问：复制时会发生什么，赋值时会发生什么，销毁时会发生什么。

接下来，我们就来依次讨论这三者。

复制构造函数的典型形式是：

```cpp
Vec(const Vec& v) { create(v.begin(), v.end()); }
```

它的职责是在“用一个已有对象去初始化一个新对象”时，构造出内容正确、资源独立的新对象。这里最容易混淆的，是复制构造与赋值运算符看上去都常常伴随等号 `=`，但它们并不是一回事。

例如：

```cpp
Vec<double> fail = hw;
```

这里虽然写了 `=`, 但本质上是在**定义新对象并用已有对象初始化它**，因此调用的是复制构造函数。相反，若写成：

```cpp
Vec<double> fail;
fail = hw;
```

这里对象 `fail` 已经存在，后面的 `=` 表示把另一个对象的内容赋给它，于是调用的是赋值运算符 `operator=`。

这就是“赋值不是初始化”的含义。两者的外观有时相似，但语义完全不同。前者是在创建对象，后者是在修改已有对象。对资源类来说，这种区别尤其关键，因为“给新对象分配资源”和“先清掉旧资源再接管新内容”是两套完全不同的工作流程。

赋值运算符的典型写法如下：

```cpp
template <class T>
Vec<T>& Vec<T>::operator=(const Vec& rhs)
{
    if (&rhs != this) {
        uncreate();
        create(rhs.begin(), rhs.end());
    }
    return *this;
}
```

这里有两个非常重要的细节。第一，要检查**自我赋值**，即 `a = a` 这种情况。若不做检查，程序可能会先把自己的资源清掉，再试图从已经被清掉的自己复制内容。第二，赋值运算符应当返回左操作数的引用，这与内置类型赋值的行为保持一致，也便于写出链式赋值表达式。

最后，我们再来看析构函数。它的职责很明确：对象生命周期结束时，把它所拥有的资源妥善清理掉。例如：

```cpp
~Vec() { uncreate(); }
```

表面上只是一句函数调用，但其背后代表着一个类的最终责任：对象离开作用域后，不仅它自己的成员值不再可见，它曾经申请过的内存和相关资源也必须被安全释放。

需要特别强调的是，编译器确实会为很多类自动生成默认的复制构造函数、赋值运算符和析构函数。对于只包含普通成员、且不直接管理外部资源的类，这些默认操作常常已经足够。但一旦类手里握着原始指针，并且这些指针指向自己申请的资源，默认操作就很可能变得危险。默认复制往往只是逐成员复制指针值，而不是复制指针所指向的内容；默认析构也不知道不同对象之间是否共享资源。这样一来，问题几乎是必然发生的。

因此，默认操作并不是“总能放心使用的懒人选项”，而是只有在类不直接负责资源时才可能合适。一旦类扮演了资源拥有者，就必须主动接管这三件事，而不能再依赖默认生成版本。

### 5.7 动态扩容：`data`、`avail`、`limit`

若一个容器只会固定大小，那它的实现当然简单一些。但向量类真正有价值的地方，在于它应当支持不断追加新元素。因此，类内部就必须能够区分三件事：

1. 当前已经分配了多少空间  
2. 当前已经构造了多少元素  
3. 当前下一次追加元素时是否还有空位

这正是三个指针 `data`、`avail`、`limit` 的意义。对应的 `push_back` 可以写成：

```cpp
void push_back(const T& val)
{
    if (avail == limit)
        grow();
    unchecked_append(val);
}
```

若 `avail == limit`，说明已构造元素的尾后位置已经碰到了整块空间的尾后位置，也就是“没有剩余容量了”。此时就必须扩容。若还有空位，则可以直接把新元素构造到 `avail` 所指的位置，然后让 `avail` 向后移动一格。

这种写法很有代表性，因为它把“检查空间是否足够”和“真正追加元素”拆成了两个动作。前者由 `grow()` 负责解决容量问题，后者由 `unchecked_append()` 负责完成对象构造。程序结构因此会更清楚，也更容易看出哪些地方在处理资源、哪些地方在处理逻辑。

### 5.8 `create`、`uncreate`、`grow` 与 `unchecked_append`

若继续沿着上面的思路往下看，一个动态向量类通常会围绕几组核心辅助函数展开。

首先是 `create`，负责申请空间并构造一批初始元素，例如：

```cpp
template <class T>
void Vec<T>::create(size_type n, const T& val)
{
    data = alloc.allocate(n);
    avail = limit = data + n;
    std::uninitialized_fill(data, limit, val);
}
```

接着是 `uncreate`，负责把已经构造过的元素逆序析构，再释放整块空间：

```cpp
template <class T>
void Vec<T>::uncreate()
{
    if (data) {
        iterator it = avail;
        while (it != data)
            alloc.destroy(--it);
        alloc.deallocate(data, limit - data);
    }
    data = avail = limit = 0;
}
```

这里逆序析构并不是偶然写法，而是对象销毁时的一般习惯：后构造的元素先析构。更重要的是，这段代码再次体现了“空间”和“对象”分开处理的思想：先析构对象，再释放空间。

然后是 `grow`，负责在容量不足时申请更大空间，把旧元素复制过去，再释放旧空间：

```cpp
template <class T>
void Vec<T>::grow()
{
    size_type new_size = std::max<size_type>(1, 2 * (limit - data));
    iterator new_data = alloc.allocate(new_size);
    iterator new_avail = std::uninitialized_copy(data, avail, new_data);

    uncreate();
    data = new_data;
    avail = new_avail;
    limit = data + new_size;
}
```

这里常见策略是按 2 倍扩容，因为若每次只多申请一个位置，频繁追加元素时开销会非常大。扩容策略本身当然不是唯一的，但“不要每次都只长 1”几乎是必然结论。

最后，`unchecked_append` 表示“在已经确认有空位的前提下，直接在尾后位置构造新元素”：

```cpp
template <class T>
void Vec<T>::unchecked_append(const T& val)
{
    alloc.construct(avail++, val);
}
```

把这几个辅助函数放在一起看，就会发现容器实现的骨架其实已经很清晰了：创建、销毁、扩容、追加，每个函数各司其职，共同维持对象内部资源的一致状态。

### 5.9 `allocator` 与未初始化内存算法

前面已经多次提到“把空间申请与对象构造分开”。标准库里承担这项工作的核心工具，就是 `allocator`。它提供了一组较底层但很有条理的操作：

- `allocate`：分配原始内存  
- `deallocate`：释放原始内存  
- `construct`：在指定位置构造对象  
- `destroy`：析构指定位置的对象

与之配套的，还有两个非常常见的未初始化内存算法：

- `uninitialized_copy`
- `uninitialized_fill`

它们的共同特点是：目标区域虽然已经有原始内存，但那上面还没有真正构造好的对象。于是，这类算法不会简单地做普通赋值，而是会在目标位置上直接构造元素。

例如，`uninitialized_fill(data, limit, val)` 可以把区间 `[data, limit)` 中的每个位置都构造成值为 `val` 的对象；`uninitialized_copy(data, avail, new_data)` 则可以把旧区间里的对象逐个复制构造到一块新空间中。

对初学者来说，`allocator` 可能是这一章里最不直观的内容之一。但只要抓住前面反复强调的核心思想，它就不再神秘：**动态内存管理的精细之处在于，空间与对象并不是同一个概念。** 先有空间，后有构造；先有析构，后有释放。`allocator` 只是把这件事情表达得更精确而已。

### 5.10 本章小结

这一章把“模板”和“资源类”这两条线第一次真正结合了起来。模板类说明，一个类也可以像函数模板那样摆脱对具体类型的依赖，从而服务于一整类元素类型。`Vec<T>` 则进一步展示了：一旦类内部开始管理动态资源，就不能再只满足于“接口能调用”，而必须认真处理构造、复制、赋值、析构、扩容和内存管理这些问题。也正是在这个过程中，`explicit`、类型别名、下标运算符、迭代器接口、复制控制、`allocator` 以及未初始化内存算法等概念被逐步串联起来。

如果说前一章开始学的是“如何设计自己的类型”，那么这一章则更进一步，开始面对真正容器类背后的内部机制。它的重要性不仅在于模板类本身，更在于它让程序员第一次系统地接触到：**一个看上去像普通值一样好用的对象，背后往往需要非常仔细的资源管理。**

## 第六章 让自定义类型像内置类型一样工作

### 本章概要

学到这里，自定义类型已经不再只是“把几项数据打包起来”的工具。读者开始真正面对一个更有挑战性、也更有意思的问题：如果一个类型设计得足够完整，它能不能像 `int`、`double`、`string` 那样自然地出现在表达式里？例如，能不能直接写下标访问、字符串拼接、输入输出、前置后置自增，甚至把对象当作一种可以自动转换的值来使用？

这正是操作符重载要解决的问题。本章的重点不是把所有运算符都背一遍，而是理解一个更深的设计目标：**让用户自定义类型在使用方式上尽量接近内置类型，同时又不破坏语言本身的规则。** 围绕这一点，本章会介绍操作符重载的基本思想，成员函数与非成员函数的分工，友元函数与友元类的作用，自动类型转换与 `explicit`，前置与后置自增，`*` 和 `->` 这样的指针式接口，以及静态成员和若干与初始化相关的重要细节。

读完这一章后，读者应当能看懂一个简单字符串类为什么会重载 `[]`、`>>`、`<<`、`+` 和 `+=`，也应当能判断某个操作符到底该写成成员函数还是非成员函数。更重要的是，读者应当逐渐明白：操作符重载真正考验的从来不只是语法，而是类型设计是否自然、对称、可靠。

### 6.1 为什么需要操作符重载

当程序员自己定义了一个类之后，最自然的愿望往往是：希望这个类不仅“能存数据”，还“好用”。例如，一个字符串类若只能通过专门的成员函数去一个字符一个字符地访问、拼接和输出，那么虽然理论上也能工作，但使用起来会显得非常笨重。相比之下，若它能像标准字符串那样支持

```cpp
s[i]
cin >> s
cout << s
s1 + s2
```

这样的写法，整个类型就会变得自然得多。

这正是操作符重载的意义所在。它并不是为了追求语法上的花哨，而是为了让某些原本就有明确直觉含义的操作，能够在自定义类型上以更自然的形式出现。比如，下标访问本来就意味着“按位置取元素”；加号本来就常用于“把两个值组合起来”；输入输出本来就常与对象的读写对应。若类的语义真的与这些动作相匹配，那么把它们重载出来，往往能让程序更像人们真正希望使用的样子。

但这里必须立刻树立一个边界意识：**操作符重载只能在语言原有规则允许的范围内进行，不能随意篡改语言本身。** 例如，重载不会改变操作数个数，不会改变优先级和结合性，也不应把一个本来含义很清楚的运算符强行解释成完全不相干的动作。因此，真正好的操作符重载，通常会让人觉得“这本来就该这么写”，而不是“这也太绕了”。

### 6.2 一个简单字符串类的启发

这一章中常见的例子，是定义一个简单的字符串类 `Str`，内部用 `Vec<char>` 保存字符序列。它的基本轮廓大致如下：

```cpp
class Str {
public:
    typedef Vec<char>::size_type size_type;

    Str() {}
    Str(size_type n, char c) : data(n, c) {}
    Str(const char* cp) {
        std::copy(cp, cp + std::strlen(cp), std::back_inserter(data));
    }

    template <class In>
    Str(In b, In e) {
        std::copy(b, e, std::back_inserter(data));
    }

private:
    Vec<char> data;
};
```

这个例子最值得注意的地方，不在于它比标准字符串强，而在于它正好展示了一个自定义类型如何一步一步变得“像字符串”。一开始，它只是一个内部持有 `Vec<char>` 的类；接下来，它会逐渐学会支持下标、输入输出、拼接和类型转换。于是，读者可以很清楚地看见：一个类型之所以好用，不是因为“底层存了字符”，而是因为**它围绕这种数据组织出了一套符合直觉的接口**。

这个例子还顺带提醒了另一个重要事实：构造函数本身也常常参与类型设计。例如 `Str(const char*)` 这种构造函数不仅能直接构造对象，还会影响后面自动类型转换和混合类型表达式能否成立。因此，本章中“构造函数”和“操作符重载”这两部分其实联系得非常紧。

### 6.3 成员还是非成员：先看对象的对称性

写操作符函数时，第一个必须面对的问题往往不是“怎么写”，而是“它应当写成成员函数，还是非成员函数”。这一点绝不能完全靠死记，应当从操作本身的结构去判断。

若某个操作显然是“某个对象对自己的内部状态做事”，那么它往往适合写成成员函数。例如下标运算符：

```cpp
char& operator[](size_type i) { return data[i]; }
const char& operator[](size_type i) const { return data[i]; }
```

这里左操作数必然是当前对象本身，语义也非常明确：就是“当前字符串按位置取字符”。这种操作天然属于对象自己，因此写成成员函数最自然。

同样，像 `operator+=` 这样的运算符也常常适合做成员函数：

```cpp
Str& Str::operator+=(const Str& s)
{
    std::copy(s.data.begin(), s.data.end(), std::back_inserter(data));
    return *this;
}
```

因为它表示“当前对象在自己尾部再接上一段内容”，会直接修改左操作数的状态。按照前面几章总结过的判断原则，这类操作通常就应当成为成员函数。

但是，并不是所有运算符都适合写成成员。最典型的就是二元 `operator+`。如果把它写成成员函数，那么像

```cpp
s1 + s2
```

这样的表达式当然没问题；可一旦希望支持

```cpp
"hello" + s2
```

就会出问题，因为左操作数不是 `Str` 对象，而是字符串字面量。成员函数调用要求左操作数就是调用它的那个对象，因此这时编译器无法先在左边那个字面量上“找到一个成员版 `operator+`”。这正说明：**若一个二元运算希望保持两边操作数的对称性，常常更适合写成非成员函数。**

### 6.4 输入输出运算符为什么通常是非成员

很多初学者第一次接触 `operator<<` 和 `operator>>` 时，会觉得它们也许可以像普通成员函数那样写进类里。但若仔细想一想表达式形式，就会发现这并不自然。因为在

```cpp
cout << s
cin >> s
```

这类写法中，左操作数是流对象，而不是自定义字符串对象。若把这两个运算符写成 `Str` 的成员函数，就会出现一种非常别扭的含义：仿佛是字符串对象在“操作流”。这与标准流的使用习惯并不一致。

因此，输入输出运算符通常应当写成非成员函数。例如：

```cpp
std::ostream& operator<<(std::ostream& os, const Str& s)
{
    for (Str::size_type i = 0; i != s.size(); ++i)
        os << s[i];
    return os;
}
```

这样的写法更符合表达式本身的方向：输出流接收右边对象中的内容，并最终把自己返回出来，以便继续支持链式写法。

输入运算符也是同理：

```cpp
std::istream& operator>>(std::istream& is, Str& s);
```

它通常要完成的工作包括：先清空旧值，再跳过前导空白，再持续读取一段非空白字符，最后把结果存回对象中。这里还有一个细节很值得注意：若函数内部用到了对象的私有数据成员，那么这个非成员函数往往需要被声明为友元。也就是说，**输入输出运算符之所以常写成非成员，是因为表达式结构决定了左操作数应当是流；而若它又确实需要接触对象内部细节，就要再配合友元机制。**

### 6.5 友元：让类在必要时有条件地开放内部细节

类设计的核心原则通常是封装，但封装并不意味着永远不允许外部接触任何内部细节。有些操作若硬要完全通过公开接口去实现，反而会显得低效或别扭。这时，C++ 提供了**友元**（friend）机制，允许类对某些特定函数或类授予内部访问权限。

最常见的情况，就是前面提到的输入运算符：

```cpp
class Str {
    friend std::istream& operator>>(std::istream& is, Str& s);
    // ...
private:
    Vec<char> data;
};
```

这样一来，`operator>>` 虽然不是 `Str` 的成员函数，却仍然可以直接访问 `s.data`。友元函数并不会变成成员函数，它只是额外获得了访问私有成员的权限。

友元还有另一种形式：**友元类**。若一个类把另一个类声明为友元类，那么那个友元类的成员函数就都能访问它的私有成员。例如：

```cpp
class A {
    friend class B;
private:
    int x;
};
```

需要特别记住的是，友元关系有几个很重要的边界。第一，它的控制权在声明者手里，也就是说，一个类只能说“我把谁当作友元”，不能单方面宣布“我去做别人的友元”。第二，友元关系通常不具有传递性。第三，友元机制本质上确实是在局部打破封装，因此应当谨慎使用。

换句话说，友元不是为了偷懒而大面积开放内部数据，而是为了在极少数确实合理的场合，让某些非成员操作也能写得自然、直接。

### 6.6 `operator[]`、`operator+=` 与 `operator+`

把几个最常见的字符串式运算放在一起看，会更容易理解成员与非成员如何配合。

先看下标运算符：

```cpp
char& operator[](size_type i) { return data[i]; }
const char& operator[](size_type i) const { return data[i]; }
```

这两个版本与之前的容器类下标接口完全一致：非常量对象返回可修改引用，常量对象返回只读引用。它们的价值不只是“可以访问字符”，更在于保持了与标准库容器一致的使用习惯。

再看 `operator+=`。它的典型语义是“把右边对象追加到当前对象后面，并返回当前对象本身”：

```cpp
Str& Str::operator+=(const Str& s)
{
    std::copy(s.data.begin(), s.data.end(), std::back_inserter(data));
    return *this;
}
```

这种“先修改左操作数，再返回左操作数引用”的模式非常重要，因为它与内置类型的 `+=` 习惯一致，也为链式表达式提供了基础。

最后看 `operator+`：

```cpp
Str operator+(const Str& s, const Str& t)
{
    Str r = s;
    r += t;
    return r;
}
```

它通常不直接修改任何一个原操作数，而是先做出左操作数的副本，再借助 `operator+=` 构造结果。这是一种很值得学习的设计方式：**把复杂的二元操作建立在更基础的复合赋值操作之上。** 这样一来，核心拼接逻辑只需维护一处，两个接口也更容易保持一致。

### 6.7 自动类型转换与混合类型表达式

当一个类提供了某些构造函数后，编译器有时会自动用它们进行类型转换。例如：

```cpp
Str s("hello");
Str t = "hello";
s = "hello";
```

第一句是显式构造，第二句是用字符串字面量初始化 `Str` 对象，第三句则是在赋值时先把右边的字面量转成临时 `Str`，再调用赋值运算。之所以这些写法能成立，关键就在于类中提供了

```cpp
Str(const char* cp)
```

这样的构造函数。

这种自动转换在混合类型表达式里尤其明显。例如：

```cpp
const Str greeting = "Hello, " + name + "!";
```

若细看其求值过程，会发现编译器需要先把字面量 `"Hello, "` 和 `"!"` 分别转换成 `Str` 对象，然后再逐步调用 `operator+`。也就是说，表达式能不能自然写出来，既依赖操作符函数本身，也依赖类是否提供了合适的构造函数作为桥梁。

这也进一步解释了为什么前面强调 `operator+` 往往要写成非成员：只有这样，左右两边的操作数才更对称，自动类型转换也更容易发挥作用。若写成成员函数，一旦左操作数不是类对象本身，表达式就会立刻变得别扭甚至无法成立。

### 6.8 `explicit` 与“危险的自动转换”

自动转换很方便，但它并不总是安全。一个重要的设计问题是：**哪些构造函数应该允许编译器自动拿来做类型转换，哪些不应该。**

一般来说，如果构造函数描述的是“对象内容的自然构造方式”，那么允许自动转换通常问题不大。例如字符串类从 `const char*` 构造，确实比较符合直觉。但若构造函数更像是在指定对象的结构，而不是对象内容，那么让它参与隐式转换就容易造成误解。

这时就应当考虑使用 `explicit`。例如：

```cpp
explicit Vec(std::size_t n, const T& val = T());
```

加上 `explicit` 之后，编译器就不能再把

```cpp
Vec<int> vi = 100;
```

自动解释为“构造一个大小为 100 的向量”。程序员必须明确地写出

```cpp
Vec<int> vi(100);
```

才表示自己真的想调用这个构造函数。

因此，`explicit` 的作用并不是“让构造函数更高级”，而是帮助类的设计者拦住那些容易引起歧义的自动转换。理解这一点之后，读者就能更清楚地判断：什么时候自动转换是一种便利，什么时候它反而会让程序变得含糊。

### 6.9 类型转换函数与流对象的布尔语境

除了“从别的类型构造当前类对象”这种转换之外，C++ 还允许类定义**类型转换函数**，把对象转换成另一种类型。例如：

```cpp
class Student_info {
public:
    operator double() const {
        // ...
    }
};
```

这表示 `Student_info` 对象可以在需要 `double` 的地方自动转成一个浮点数。比如若这个类把自己转换成某种成绩值，那么表达式里就可能直接把对象和数值一起计算。

不过，类型转换函数与自动构造一样，也是一把双刃剑。它的便利性很高，但如果设计得太随意，也会让表达式的真实含义变得不清楚。因此，这类接口往往更适合那些“转换目标非常自然、不会引起误解”的场合。

标准输入流里其实也有一个很经典的例子。以前常见的写法：

```cpp
while (cin >> x) {
    // ...
}
```

之所以能工作，本质上也是因为流对象能在条件判断的语境下被转换为一种“可判断真假的状态值”。历史上这常通过到 `void*` 之类的转换来实现，核心含义则始终一致：当流状态良好时，这个对象在布尔环境下应当表现为真；一旦读取失败，就表现为假。这个例子很有价值，因为它说明类型转换并不一定是“把对象变成数值”，它也可以是“把对象变成某种状态意义上的真假”。

### 6.10 前置与后置自增为什么是两种不同运算

自增运算看起来很熟悉，但在重载时必须把前置和后置严格区分开来。前置自增 `++i` 的语义是“先加一，再把新值作为结果”；后置自增 `i++` 的语义则是“先保留旧值作为结果，再让对象自己加一”。也正因为返回语义不同，两者的实现形式也不同。

典型写法是：

```cpp
class A {
public:
    A& operator++() {
        n++;
        return *this;
    }

    A operator++(int) {
        A old(n);
        n++;
        return old;
    }
};
```

其中，前置版本没有额外参数，返回的是当前对象引用；后置版本则要带一个无意义的 `int` 占位参数，用来与前置版本区分开。后置版本通常需要先保存旧值，因此返回的往往是一个值对象，而不是引用。

这一组运算符非常适合用来理解“语义决定接口”这件事。看上去只是一个小小的 `int` 参数差别，背后对应的其实是完全不同的返回行为。只要把“前置返回新状态，后置返回旧状态”这条逻辑抓住，实现形式就会顺理成章。

### 6.11 `*` 与 `->`：让对象表现得像指针

有些类虽然本身不是原始指针，却希望在使用方式上表现出“像指针一样访问所指对象”的感觉。最典型的场景就是迭代器和智能指针。这时，类可以重载 `*` 和 `->`。

最基础的形式是：

```cpp
T& operator*() const;
T* operator->() const;
```

含义也很直观：`*` 用于取得当前指向对象本身，`->` 用于继续访问该对象的成员。一个简化迭代器的例子可以写成：

```cpp
template <typename T>
class Iterator {
public:
    Iterator(ListNode<T>* n = 0) : node(n) {}

    T& operator*() const { return node->data; }
    T* operator->() const { return &(node->data); }

    Iterator& operator++() {
        node = node->next;
        return *this;
    }

private:
    ListNode<T>* node;
};
```

这样一来，使用者就能写出

```cpp
(*iter).name
iter->name
```

这类与标准迭代器非常接近的表达式。它们之所以自然，并不是因为类真的变成了原始指针，而是因为类提供了符合指针直觉的接口。

因此，这组重载再一次说明了操作符设计的根本目标：不是追求技巧，而是让对象在语义上尽量贴近使用者原本熟悉的操作方式。

### 6.12 常量成员、引用成员与初始化列表

当类中出现**常量数据成员**或**引用数据成员**时，构造函数的写法就会变得格外讲究。例如：

```cpp
class C {
public:
    C(int& r) : nine(9), refR(r) {}

private:
    const int nine;
    int& refR;
};
```

这里 `nine` 是常量成员，`refR` 是引用成员。它们都必须在初始化列表中完成初始化，而不能等到构造函数体内再赋值。原因并不复杂：常量成员一旦对象创建完成就不能被重新赋值；引用成员也必须在诞生时就绑定到某个确定对象上，之后不能改绑到别处。

因此，下面这种写法就是错误的：

```cpp
C(int& r) {
    nine = 9;
    refR = r;
}
```

因为这里已经不是“初始化”，而是在试图给一个早该初始化好的成员赋值。这个例子非常值得记住，因为它把初始化列表的重要性提升到了“不是建议，而是必须”的程度。

换句话说，初始化列表并不只是“更高效的一种风格写法”。在某些成员类型下，它就是唯一正确的构造方式。

### 6.13 静态成员：属于类，而不属于某个对象

前面学过的普通数据成员，都是“每个对象各自有一份”。而**静态成员**（static member）则不同，它属于整个类，而不属于任何某个具体对象。也就是说，这个类的所有对象共享同一份静态数据。

这类设计在以下场景中很自然。例如，一个类想统计“自己总共创建了多少个对象”，那么计数器显然不应当分散地放在每个对象内部，而应当放成类级别的一份共享数据。又如，一组对象若要被链接成链表，那么整个类共享一个头指针也很常见。

典型形式如下：

```cpp
class Link {
public:
    static Link* findEle(int x, int y);

private:
    int X, Y;
    Link* next;
    static Link* head;
};
```

这里 `head` 就是静态数据成员，`findEle` 是静态成员函数。静态成员函数之所以特别，是因为它并不依附于某一个具体对象，所以它内部不能像普通成员函数那样直接使用某个对象的非静态成员，除非先通过指针或对象显式地访问。

静态数据成员还必须在类外进行一次定义，例如：

```cpp
int A::count = 0;
Link* Link::head = 0;
```

这一步非常重要，因为类内声明只是在说明“这个类里有这样一个静态成员”，真正为它分配存储空间仍需要类外定义。

而在类外访问公共静态成员时，也通常有两种写法：

```cpp
对象名.静态成员名
类名::静态成员名
```

从语义上看，第二种写法往往更能体现“它属于类而不是对象”的本质，因此也更常见。

### 6.14 本章小结

这一章真正展开的是一个很重要的目标：让用户自定义类型在使用方式上尽量接近内置类型。操作符重载提供了这种可能，但它并不只是语法技巧，而是接口设计的一部分。下标运算符、输入输出运算符、`+=` 与 `+` 的分工说明了成员函数和非成员函数应如何协作；自动构造与 `explicit` 说明了类型转换既可能带来便利，也可能制造歧义；友元机制则在局部开放内部细节与保持封装之间提供了平衡；前置与后置自增、`*` 与 `->` 又进一步展示了：一个类可以在多大程度上表现得像内置类型或指针。

与此同时，本章还把若干看似分散但实际非常重要的细节连在了一起，例如常量成员与引用成员的初始化、类型转换函数、静态成员的类级语义等。这些内容共同说明了一点：**一个类型是否“好用”，不只取决于它能不能工作，更取决于它能不能以符合直觉、符合语言习惯的方式工作。**

### 本章小练习

1. 选择题  
对于一个自定义字符串类 `Str`，若希望支持 `cout << s` 以及 `"abc" + s` 这类表达式，下面说法正确的是（ ）

A. `operator<<` 和 `operator+` 都必须写成成员函数  
B. `operator<<` 通常适合写成非成员函数，`operator+` 也常适合写成非成员函数  
C. `operator+` 必须写成成员函数，否则不能访问对象  
D. `operator<<` 必须写成友元成员函数

2. 程序阅读题  
阅读下面程序，写出输出结果，并简要说明原因。

```cpp
#include <iostream>
using namespace std;

class Counter {
public:
    Counter(int x = 0) : n(x) {}

    Counter& operator++() {
        ++n;
        return *this;
    }

    Counter operator++(int) {
        Counter old = *this;
        ++n;
        return old;
    }

    int value() const { return n; }

private:
    int n;
};

int main() {
    Counter c(5);
    Counter a = ++c;
    Counter b = c++;
    cout << a.value() << " " << b.value() << " " << c.value() << endl;
    return 0;
}
```

3. 程序填空题  
下面给出一个简单类。请在空白处填入合适代码，使输入运算符能够访问对象的私有成员 `data`。

```cpp
#include <iostream>
#include <string>
using namespace std;

class Word {
    ________________________________
public:
    Word() : data("") {}

private:
    string data;
};

istream& operator>>(istream& is, Word& w) {
    is >> w.data;
    return is;
}
```

### 参考解答

1. 正确答案是 `B`。  
输入输出运算符的左操作数是流对象，因此通常应写成非成员函数；而二元 `operator+` 若希望两边操作数保持对称，并支持字面量或其他可自动转换对象出现在左侧，往往也更适合写成非成员函数。

2. 输出为

```text
6 6 7
```

原因如下。开始时 `c` 的值为 `5`。执行 `++c` 时，前置自增先把 `c` 改为 `6`，再返回修改后的对象，因此 `a` 得到的值是 `6`。接着执行 `c++` 时，后置自增先保存旧值 `6` 作为返回结果，再把 `c` 自己加到 `7`，所以 `b` 得到的值是 `6`，而最终 `c` 的值变成 `7`。

3. 空白处应填入

```cpp
friend istream& operator>>(istream& is, Word& w);
```

补全后，这个输入运算符虽然不是类的成员函数，但由于被声明为友元函数，因此可以直接访问对象 `w` 的私有成员 `data`。这正是友元在输入输出运算符场景中的典型用途。
